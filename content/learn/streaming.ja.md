# ストリーミングとリアルタイムテキスト

トークンストリーム（LLMチャット）、ログテール、ライブデータフィードは、素朴なVectoJSコードが最も頻繁に破綻する場面です。エンジンは高速なプリミティブ——`Text.append()`、`Markdown.appendMarkdown()`、段落レベルのレイアウトメモ化、オフスレッドのMarkdownパース——を提供しますが、これらをフレーム単位ではなくトークン単位で配線すると、その利点のほとんどが失われます。このページでは、エンドツーエンドのレシピを提供します。

## 唯一のルール：トークン単位ではなく、フレーム単位でコミットする

ストリームは、ディスプレイのリフレッシュ速度よりはるかに速くトークンを届けます。`appendMarkdown()`を直接呼び出すと、そのたびにパースとレイアウトのパスが発生し、レンダリングされた2つのフレームの間にあるパスは、最後のものを除いてすべて**不可視の作業**になります。独自のスケジューラーを実装するのではなく、組み込みの `StreamController` を使用してください：

```typescript
const stream = markdown.createStream();

try {
  for await (const token of llmStream) {
    await stream.write(token);
  }
  await stream.close(); // 最後のコミットを強制します。次のフレームを待たないでください
} catch (error) {
  stream.abort(error); // 受け入れられたがコミットされていないテキストを破棄します
  throw error;
}
```

デフォルトのモードでは、受け入れたチャンクを個別の文字列として保持し、次のアニメーションフレームで最大1回結合してコミットします。`write()` は、チャンクが可視になったときではなく、上限付きバッファに入った時点で解決されるため、1つの非同期プロデューサーが同じフレーム内で複数のトークンを提供することができます。必ず `await` してください：64 KiB の上限付きバッファがいっぱいになると、一度の書き込みは容量が空くまで待機し、無制限のキューを作成する代わりに、それ以上の書き込みは拒否（reject）されます。

60 fpsで実行される200トークン/秒のストリームの場合、これにより1秒あたり最大約200回のレイアウトパスが最大約60回に減少します。負荷がかかった状態では適切にダウングレードします：メインスレッドが忙しくなるほど、コミットされるチャンクは大きく（そして*稀に*）なります。固定の `setInterval` によるデバウンスはその逆の結果を招きます。

`appendMarkdown()` は依然として同期的なエスケープハッチです。直接呼び出すと、まずこれまでに送信されたすべてのコントローラーテキスト（バックプレッシャーを受けた1回の書き込みを含む）がフラッシュされ、その後自身のチャンクが追加されるため、呼び出しの順序は正確に保たれます。

> [!NOTE]
> `scene.markDirty()` は既に自然に結合されます——1つのフレーム内での3回の追加は1つのフラグを設定し、1回の再描画コストになります。コストが高いのはパースとレイアウトの部分であり、それがバッチ処理が `appendMarkdown()` 自体をラップしなければならない理由です。`createStream()` はまさにそれを行います。別のパーサーや調整パスを作成するわけではありません。

## 追加APIの選択

| コンテンツ               | API                                                      | コミットごとのコスト                                                                           |
| ------------------------ | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| プレーンテキスト         | `text.append(chunk)`                                     | コールドパスですが、段落メモ化により完了した `\n` 終端の段落はすべて再利用されます             |
| スタイル付きスパン       | `richText.appendSpans(spans)`                            | スパンを追加します；以前のスパンの測定値は再利用されます                                       |
| Markdown、直接           | `markdown.appendMarkdown(chunk)`                         | 同期 API；呼び出しごとに追加コミットが1回発生します                                            |
| Markdown、ストリーム     | `createStream()` 後、`await stream.write(chunk)`         | 1アニメーションフレームにつき最大1回の追加コミット；上限付きプロデューサーのバックプレッシャー |
| 任意のコンテンツ、置換型 | `setText` / `setContent`（ストリーミングアンチパターン） | 完全な再構築——トークンごとに成長するドキュメントで呼び出さないでください                       |

`appendMarkdown` の内部には、知っておくべき2つのコストが隠されています：

1. **字句解析はチャンク単位ではなくドキュメント単位で O(ドキュメント) です。** 呼び出しごとに蓄積されたソース全体が再トークン化されます。パースは利用可能な場合バックグラウンドの Worker で実行され（`Worker` がない環境では同期的な字句解析にフォールバックします）、エンティティの更新では完了したすべてのブロックが再利用されます——しかし、10万文字のトランスクリプトではフラッシュごとに10万文字の字句解析コストがかかります。フレームごとのバッチ処理はこのコストを（フレームあたりのトークン数で）分割します。後述のトランスクリプトのセグメント化はこれを制限します。

2. **段落メモ化は `\n` をキーとします。** `Text.append` および Markdown の段落アップデーターは、変更された段落のみを再測定します。終わりのない連続した行はメモ化を無効にし、フラッシュごとに O(ドキュメント) の測定へと劣化させます。LLM の出力には自然な段落の区切りがあり、ログの行は `\n` で終わります——通常は自動的に恩恵を受けますが、改行を削除しないでください。

## タイプライターのペーシングとライフサイクル

パフォーマンスのためのバッチ処理がデフォルトです。製品がタイプライターのような表示を必要とする場合にのみ、固定のウォールクロックペーシングを追加してください：

```typescript
const stream = markdown.createStream({
  pacing: { graphemesPerSecond: 48 },
  maxBufferedChars: 64 * 1024,
  signal: requestAbort.signal,
});
```

ペーシングは「フレームごとに1トークン」に切り替わるわけではありません。rAF のタイムスタンプから `graphemesPerSecond`（1秒あたりの書記素数）のクレジットを蓄積し、1フレームで複数の書記素を表示する可能性があり、追加コミットも最大1回しか実行しません。100msのタイムスタンプ上限により、バックグラウンドのタブが突然大量の遅延コンテンツを吐き出すのを防ぎます。

スライスには `Intl.Segmenter` が使用され、チャンク/フレームの境界を越えても機能するため、結合マーク、絵文字の ZWJ シーケンス、フラグ、サロゲートペアは一緒に保持されます。Unicode では単一の書記素が制限なく拡張することが許されています；悪意のある入力が境界に到達することなく上限付き（受け入れ済み＋ブロック済み）のウィンドウ全体を埋め尽くした場合、コントローラーはデッドロックや際限のないメモリ増加を引き起こすのではなく、1つの Unicode コードポイントを（決してサロゲートペアの半分ではなく）コミットします。

- `flush()` は、送信されたテキストを同期的にコミットし、ストリームを開いたままにします。
- `close()` はブロックされた書き込みを許可し、保持されていた書記素の末尾を解放し、最後に1回の順序付けられたコミットを実行してストリームを閉じます。
- `abort(reason)` は未コミットのテキストを破棄します。保留中および将来の操作は、保持された拒否の理由（reason）で拒否されます。
- `Markdown.setContent()` は、置換を行う前にアクティブなコントローラーを中止します。
- `Markdown.destroy()` はコントローラーを中止し、rAF/`AbortSignal` リスナーを削除します。
- 1つの `Markdown` が持つ開いているコントローラーは最大1つです。終了したコントローラーは登録解除され、後続のストリームを開始できるようになります。

## レンダリングモードとアイドルスロットル

ストリーミングUIは `renderMode: 'onDemand'` を使用して実行すべきです：

```typescript
const scene = new Scene(canvas, { renderMode: 'onDemand' });
```

追加のたびにシーンはダーティとしてマークされるため、コンテンツが流れている間だけフレームがレンダリングされ、ストリームがアイドル状態になった瞬間に停止します——2 fpsの自動スロットルによる予期せぬ動作や、応答間の不要なバッテリー消費はありません。追加 API や組み込みのスクロールコンテナはすべて進行中のアニメーションを報告する（`hasPendingAnimations()`）ため、一番下までスムーズにスクロールする動作は最後のトークンが到着した後もアニメーションを継続します。

ストリーム中に `update()` から**カスタム**のフレームごとの動き（タイピングインジケーター、点滅するカーソルなど）を駆動する場合は、[アイドル自動スロットルの隠れた落とし穴](/learn/performance/#アイドル自動スロットル隠れた落とし穴)に注意してください：`hasPendingAnimations()` をオーバーライドするか、`animate()`/`springTo()` で駆動してください。

## 下端に追従する

`ScrollView.scrollToBottom()` はコンテンツの末尾に**スナップ**します——これは意図的にスクロールスプリングをバイパスしています。なぜなら、1秒間に何度もスプリングのターゲットを再設定すると決して安定せず、最新のコンテンツを追跡する代わりにビューポートがガタガタ揺れるからです。`Markdown.onLayoutUpdated` は、各ストリームコミットの後、新しい高さが利用可能になったときに実行されます：

```typescript
let stickToBottom = true;

function nearBottom(sv: ScrollView, slack = 24): boolean {
  const maxScroll = Math.max(0, sv.content.height - sv.height);
  return -sv.content.y >= maxScroll - slack;
}

markdown.onLayoutUpdated = () => {
  if (stickToBottom) transcript.scrollToBottom();
};

for await (const token of llmStream) {
  // コミットによってコンテンツの高さが変わる前に、意図を読み取ります。
  stickToBottom = nearBottom(transcript);
  await stream.write(token);
}
await stream.close();
```

また、アプリのユーザースクロール処理で `stickToBottom = false` を設定してください。そうしないと、最後の保留フレーム中にスクロールしたユーザーが、古い意図によって強制的に下に戻されてしまう可能性があります。順序がここでは重要です：コンテンツが成長する前に「一番下にいたか」を読み取り、`onLayoutUpdated` の後にのみスナップします。

> [!NOTE]
> `scrollTo(y)` はスクロール**スプリング**のターゲットを再設定しますが、`scrollToBottom()` は**スナップ**します。`scrollTo` の直後に位置から派生した状態を読み取ると、依然として古い位置が見えます——後続のコミット/フレームで読み取ってください。

## 長時間トランスクリプト：セグメント化し、仮想化する

追加コストと字句解析コストはどちらもドキュメントのサイズに応じて増加するため、ドキュメントのサイズに上限を設けてください。チャット/ログ UI のための2層戦略：

1. **メッセージごとにセグメント化する。** アシスタントのメッセージごとに1つの `Markdown` エンティティを使用し、会話全体で1つにしないでください。ストリーミングエンティティは常に小さく（現在転送中のメッセージのみ）保たれるため、会話の長さに関係なくフラッシュごとの字句解析コストは安価なままです。完了したメッセージは一切再字句解析されません。
2. **履歴を仮想化する。** メッセージが個別のエンティティになったら、[`VirtualList`](/reference/ui-virtuallist/) は可視部分のみをレンダリングします。数千件のメッセージを含むトランスクリプトのコストは、セッションに蓄積された量ではなく、ビューポートに表示されている内容のみに依存します。

```typescript
function startAssistantMessage(): Markdown {
  const md = new Markdown('', { maxWidth: 640 });
  messages.push(md); // VirtualListのデータソース
  return md; // このエンティティのみにストリーミングします
}
```

これによりメモリも制限されます：完了したメッセージの静的なレイアウトはカリング可能であり、はるか昔に遡ってスクロールしても、ライブテールの再レイアウトがトリガーされることはありません。

## ストリーミングUIの測定

症状とそのシグナル、確認すべき順序：

| 症状                                                 | プローブ                                                                                                                                                   |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ストリーミング中のジャンク（カクつき）               | DevTools の `Streaming/appends` がレンダリングされたフレーム数を超えている——ライブメッセージごとに `createStream()` を1つ使用してください                  |
| 負荷下で `write()` が拒否される                      | バックプレッシャーがかかっている間に2つ目の書き込みが到着した——各書き込みを必ず `await` してください                                                       |
| トランスクリプトが長くなるにつれてジャンクが増大する | 成長し続ける1つのエンティティにストリーミングしている——メッセージごとにセグメント化してください                                                            |
| 長い段落で UI 全体がストールする                     | ストリームに `\n` がない——段落メモ化が分割できません；ソースのフォーマットを確認してください                                                               |
| スクロールがユーザーの操作と競合する                 | `scrollToBottom()` が無条件で呼び出されている——「一番下にいたか」のスナップ判定で制限してください                                                          |
| ストリームがアイドル状態なのに CPU がビジー          | シーンが `'always'` モードのままになっているか、`hasPendingAnimations()` を使用しないカスタムアニメーションがある；コントローラーの rAF はアイドル状態です |

実際の数値については、[実際のパフォーマンスの測定](/learn/performance/#実際のパフォーマンスの測定) に記載されているページ内の測定パターンを使用してください——ヘッドレスの FPS は代表的なものではありません。
