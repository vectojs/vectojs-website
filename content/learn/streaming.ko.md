# 스트리밍 및 실시간 텍스트

토큰 스트림(LLM 채팅), 로그 테일 및 실시간 데이터 피드는 순진한 VectoJS 코드가 가장 흔하게 절벽에서 떨어지는 곳입니다. 엔진은 빠른 원시 함수들—`Text.append()`, `Markdown.appendMarkdown()`, 단락 수준의 레이아웃 메모이제이션, 오프 스레드 Markdown 파싱—을 제공하지만, 이를 프레임 단위가 아닌 토큰 단위로 연결하면 그 장점의 대부분을 버리게 됩니다. 이 페이지에서는 완전한 종단 간 해결책(end-to-end recipe)을 제공합니다.

## 단일 규칙: 토큰 단위가 아닌 프레임 단위로 커밋하기

스트림은 디스플레이가 새로 고쳐지는 것보다 훨씬 빠르게 토큰을 전달합니다. `appendMarkdown()`을 직접 호출할 때마다 파싱/레이아웃 패스가 발생할 수 있으며, 렌더링된 두 프레임 사이의 모든 패스(마지막 패스 제외)는 **보이지 않는 작업**이 됩니다. 두 번째 스케줄러를 직접 구성하는 대신 기본 제공되는 `StreamController`를 사용하세요:

```typescript
const stream = markdown.createStream();

try {
  for await (const token of llmStream) {
    await stream.write(token);
  }
  await stream.close(); // 최종 커밋 강제 실행; 다음 프레임을 기다리지 않음
} catch (error) {
  stream.abort(error); // 허용되었으나 커밋되지 않은 텍스트 폐기
  throw error;
}
```

기본 모드는 허용된 청크를 개별 문자열로 유지한 다음 다음 애니메이션 프레임에서 최대 한 번 병합하고 커밋합니다. `write()`는 청크가 표시될 때가 아니라 제한된 버퍼에 들어갈 때 확인(resolve)되므로, 비동기 생산자는 여전히 동일한 프레임에 여러 토큰을 제공할 수 있습니다. `await`를 사용하세요: 64 KiB 고수위(high-water) 버퍼가 가득 차면 한 번의 쓰기는 용량이 생길 때까지 대기하고, 무제한 대기열을 생성하는 대신 추가 쓰기는 거부(reject)됩니다.

60fps로 실행되는 200토큰/초 스트림의 경우, 이를 통해 초당 최대 약 200회의 레이아웃 패스가 최대 약 60회로 줄어듭니다. 부하가 걸린 상태에서도 우아하게 저하됩니다: 메인 스레드가 바쁠수록 커밋되는 청크가 더 커지고(_드물어짐_) 안정적으로 유지됩니다. 고정된 `setInterval` 디바운스는 그 반대입니다.

`appendMarkdown()`은 여전히 동기적인 탈출구입니다. 직접 호출하면 먼저 이전에 제출된 모든 컨트롤러 텍스트(백프레셔된 쓰기 하나 포함)를 플러시한 다음 자신의 청크를 추가하므로 호출 순서가 정확하게 유지됩니다.

> [!NOTE]
> `scene.markDirty()`는 이미 자연스럽게 병합됩니다 — 한 프레임에서 세 번의 추가는 하나의 플래그를 설정하고 단일 다시 그리기를 요구합니다. 비용이 많이 드는 부분은 파싱/레이아웃이며, 이것이 배치 처리가 `appendMarkdown()` 자체를 감싸야 하는 이유입니다. `createStream()`은 정확히 이 작업을 수행합니다. 다른 파서나 조정 경로를 생성하지 않습니다.

## 추가 API 선택

| 콘텐츠               | API                                             | 커밋당 비용                                                                    |
| -------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------ |
| 일반 텍스트          | `text.append(chunk)`                            | 콜드 패스이지만, 단락 메모이제이션은 완성된 `\n` 종료 단락을 모두 재사용합니다 |
| 스타일이 적용된 스팬 | `richText.appendSpans(spans)`                   | 스팬을 추가합니다. 이전 스팬의 측정값이 재사용됩니다                           |
| Markdown, 직접 추가  | `markdown.appendMarkdown(chunk)`                | 동기 API. 호출당 하나의 추가 커밋이 발생합니다                                 |
| Markdown, 스트리밍   | `createStream()` 후 `await stream.write(chunk)` | 애니메이션 프레임당 최대 하나의 추가 커밋. 제한된 생산자 백프레셔              |
| 무엇이든, 덮어쓰기   | `setText` / `setContent` (스트리밍 안티 패턴)   | 전체 재구축 — 토큰 단위로 커지는 문서에서 절대 호출하지 마십시오               |

`appendMarkdown` 내부에는 알아야 할 두 가지 비용이 숨어 있습니다:

1. **렉싱은 증분식이며, 불안정한 꼬리를 키로 사용합니다.** 0.8.1부터 워커 경로는 누적된 전체 소스를 다시 토큰화하는 대신 마지막 안정적인 블록 경계(`lexAppend`)부터 다시 렉싱하므로 청크당 비용은 문서 크기가 아니라 변경된 꼬리를 추적합니다. 링크 정의 블록이나 줄 시작의 `$$` 수학을 사용하는 문서만 전체 문서 렉싱(`lexFull`)으로 대체됩니다. 파싱은 사용 가능한 경우 백그라운드 Worker에서 실행되고(`Worker`가 없는 환경에서는 동기식 렉싱으로 대체), 엔터티 업데이트는 완성된 모든 블록을 재사용합니다.

2. **단락 메모이제이션의 키는 `\n`입니다.** `Text.append` 및 Markdown 단락 업데이터는 변경된 단락만 다시 측정합니다. 끝없는 한 줄의 문장은 메모이제이션을 무효화하고 플러시당 O(문서) 측정으로 성능을 저하시킵니다. LLM 출력에는 자연스러운 단락 끊기가 있고, 로그 줄은 `\n`으로 끝납니다 — 일반적으로 이를 무료로 얻게 되지만, 줄바꿈을 제거하지 마십시오.

## 타자기 페이싱 및 수명 주기

성능을 위한 배치 처리가 기본값입니다. 제품에 타자기 노출 효과가 필요한 경우에만 고정된 물리적 시간 페이싱을 추가하십시오:

```typescript
const stream = markdown.createStream({
  pacing: { graphemesPerSecond: 48 },
  maxBufferedChars: 64 * 1024,
  signal: requestAbort.signal,
});
```

페이싱은 "프레임당 하나의 토큰"으로 전환되지 않습니다. rAF 타임스탬프에서 `graphemesPerSecond`(초당 자소 수) 크레딧을 누적하고, 한 프레임에 여러 자소를 노출할 수 있으며, 여전히 최대 한 번의 추가 커밋만 수행합니다. 100ms의 타임스탬프 상한선은 백그라운드 탭이 누적된 대량의 콘텐츠를 갑자기 쏟아내는 것을 방지합니다.

슬라이싱은 청크/프레임 경계를 넘어서도 `Intl.Segmenter`를 사용하므로 결합 마크, 이모지 ZWJ 시퀀스, 플래그 및 대리자 쌍(surrogate pairs)이 함께 유지됩니다. Unicode는 단일 자소가 제한 없이 커지는 것을 허용합니다. 악의적인 입력이 경계에 도달하지 않고 완전히 제한된(허용된 것 + 차단된 것) 창을 채우는 경우, 컨트롤러는 교착 상태(deadlock)에 빠지거나 메모리를 무제한으로 늘리지 않고 단일 Unicode 코드 포인트(절대 대리자 쌍의 절반이 아님)를 커밋합니다.

- `flush()`는 제출된 텍스트를 동기식으로 커밋하고 스트림을 열어 둡니다.
- `close()`는 차단된 쓰기를 허용하고 유지된 자소 끝을 해제하며 마지막 순서의 커밋을 한 번 수행하고 닫습니다.
- `abort(reason)`는 커밋되지 않은 텍스트를 폐기합니다. 대기 중이거나 향후의 작업은 유지된 이유(reason)로 거부됩니다.
- `Markdown.setContent()`는 교체 전에 활성화된 컨트롤러를 중단합니다.
- `Markdown.destroy()`는 컨트롤러를 중단하고 rAF/`AbortSignal` 리스너를 제거합니다.
- 하나의 `Markdown`은 최대 하나의 열린 컨트롤러를 소유합니다. 종료된 컨트롤러는 등록 취소되므로 이후의 스트림이 시작될 수 있습니다.

## 렌더링 모드 및 유휴 스로틀

스트리밍 UI는 `renderMode: 'onDemand'`로 실행해야 합니다:

```typescript
const scene = new Scene(canvas, { renderMode: 'onDemand' });
```

추가될 때마다 씬(scene)을 더티(dirty)로 표시하므로, 프레임은 콘텐츠가 흐르는 동안에만 정확히 렌더링되고 스트림이 유휴 상태가 되는 순간 중지됩니다 — 2fps 자동 스로틀에 따른 놀라움이 없으며, 응답 사이의 유휴 상태에서 불필요한 배터리 소모도 없습니다. 추가 API 및 내장 스크롤 컨테이너는 모두 진행 중인 애니메이션을 보고하므로(`hasPendingAnimations()`), 가장 아래로 부드럽게 스크롤하는 동작은 마지막 토큰이 도착한 후에도 애니메이션을 유지합니다.

스트림 중에 `update()`에서 커스텀 프레임 단위 모션(예: 타이핑 표시기, 깜박이는 커서)을 구동하는 경우 [유휴 자동 스로틀 계약](/learn/performance/#yuhyu-jadong-seuroteul-sumeun-hamjeong)을 기억하십시오: `hasPendingAnimations()`를 재정의(override)하거나 `animate()`/`springTo()`로 구동하십시오.

## 아래쪽을 따라가기

`ScrollView.scrollToBottom()`은 콘텐츠의 끝으로 **스냅(snap)**합니다. 스프링의 목표를 초당 여러 번 재지정하면 결코 안정을 찾지 못하고 최신 콘텐츠를 추적하는 대신 뷰포트가 떨리기 때문에 의도적으로 스크롤 스프링을 우회합니다. `Markdown.onLayoutUpdated`는 새로운 높이를 사용할 수 있게 되는 각 스트림 커밋 후에 실행됩니다:

```typescript
let stickToBottom = true;

function nearBottom(sv: ScrollView, slack = 24): boolean {
  const maxScroll = Math.max(0, sv.content.height - sv.height);
  return -sv.content.y >= maxScroll - slack;
}

markdown.onLayoutUpdated = () => {
  if (stickToBottom) transcript.scrollToBottom();
};

for await (const token of llmStream) {
  // 커밋으로 인해 콘텐츠 높이가 변경되기 전에 의도를 읽습니다.
  stickToBottom = nearBottom(transcript);
  await stream.write(token);
}
await stream.close();
```

앱의 사용자 스크롤 처리에서 `stickToBottom = false`를 설정해야 합니다. 그렇지 않으면 마지막 보류 프레임 동안 스크롤한 사용자가 오래된 의도에 의해 뒤로 스냅될 수 있습니다. 순서가 변하지 않는 원칙입니다: 콘텐츠가 늘어나기 전에 "아래쪽에 있었는지"를 읽고, `onLayoutUpdated` 후에만 스냅(snap)하십시오.

> [!NOTE]
> `scrollTo(y)`는 스크롤 **스프링**을 재지정하는 반면, `scrollToBottom()`은 **스냅**합니다. `scrollTo` 직후 위치에서 파생된 상태를 읽으면 여전히 이전 위치가 표시됩니다 — 후속 커밋/프레임에서 읽으십시오.

## 긴 트랜스크립트: 세분화한 다음 가상화

추가 비용과 렉싱 비용 모두 문서 크기에 비례하여 증가하므로 문서 길이를 제한하십시오. 채팅/로그 UI를 위한 2단계 전략:

1. **메시지당 세분화.** 대화 전체에 하나를 사용하는 것이 아니라, 어시스턴트 메시지당 하나의 `Markdown` 엔터티를 사용합니다. 스트리밍 엔터티는 항상 작게(진행 중인 메시지만) 유지되므로 대화 길이와 관계없이 플러시당 렉싱 비용이 저렴하게 유지됩니다. 완료된 메시지는 다시 파싱되지 않습니다.
2. **기록의 가상화.** 메시지가 별도의 엔터티가 되면 [`VirtualList`](/reference/ui-virtuallist/)는 보이는 항목만 렌더링합니다. 수천 개의 메시지가 있는 트랜스크립트의 비용은 세션에 누적된 내용이 아니라 뷰포트에 표시되는 내용에 따라 달라집니다.

```typescript
function startAssistantMessage(): Markdown {
  const md = new Markdown('', { maxWidth: 640 });
  messages.push(md); // VirtualList 데이터 소스
  return md; // 이 엔터티에만 스트리밍
}
```

이 방법은 메모리도 제한합니다: 완료된 메시지의 정적 레이아웃은 폐기(cull)할 수 있으며, 뒤로 멀리 스크롤해도 라이브 테일의 레이아웃이 다시 트리거되지 않습니다.

## 스트리밍 UI 측정

확인해야 할 순서대로 증상 및 신호:

| 증상                               | 진단 수단                                                                                                                                  |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 스트리밍 중 끊김                   | DevTools `Streaming/appends`가 렌더링된 프레임을 초과함 — 라이브 메시지당 하나의 `createStream()`을 사용하십시오                           |
| 부하 상태에서 `write()` 거부       | 백프레셔가 걸려 있는 동안 두 번째 쓰기가 도착함 — 각 쓰기를 `await`하십시오                                                                |
| 트랜스크립트 길이에 따라 끊김 증가 | 끊임없이 커지는 하나의 엔터티로 스트리밍 중임 — 메시지당 세분화하십시오                                                                    |
| 긴 단락에서 UI 전체가 멈춤         | 스트림에 `\n`이 없음 — 단락 메모이제이션을 분할할 수 없습니다. 원본 형식을 확인하십시오                                                    |
| 스크롤이 사용자의 동작과 충돌함    | `scrollToBottom()`이 무조건 호출됨 — "아래쪽에 있었는지" 접착성 판단을 통해 제한하십시오                                                   |
| 스트림이 유휴 상태인데 CPU가 바쁨  | 씬(scene)이 `'always'` 모드로 남아 있거나, `hasPendingAnimations()`를 사용하지 않는 커스텀 애니메이션이 있음; 컨트롤러의 rAF는 유휴 상태임 |

실제 측정값을 원한다면 [실제 성능 측정](/learn/performance/#silje-seongneung-ceugjeong)에 소개된 페이지 내 측정 패턴을 사용하십시오 — 헤드리스 FPS는 대표성이 없습니다.

> **다음:** 완전한 최적화 도구 모음은 [성능](/learn/performance/), 스트리밍 API 레퍼런스는 [`Markdown`](/reference/ui-markdown/)을 참조하세요.
