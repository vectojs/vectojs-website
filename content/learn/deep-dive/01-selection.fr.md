# 01 — Sélection Canvas-Native — Parité Dual-World

> Une toile est de l'encre sur un bitmap. La machinerie de sélection du navigateur — `Range`,`Selection`,`getBoundingClientRect`,`copy`,`find-in-page`, IME — réside dans le DOM. VectoJS maintient deux mondes alignés à chaque image : le **monde visuel** (ce que le GPU dessine) et le **monde de sélection DOM** (ce que le navigateur peut sélectionner). Ce document est le contrat entre eux.

## 1. Pourquoi Canvas n'a pas de sélection

Le DOM donne au texte trois choses gratuitement :

1. **Géométrie d'accès** — `Range.getClientRects()` renvoie les propres boîtes disposées du navigateur pour n'importe quelle sous-chaîne.
2. **Source du presse-papiers** — L'événement `textContent`+`Selection.toString()`+`copy` donne au navigateur une chaîne linéaire à sérialiser.
3. **Surface d'édition** — `<input>`/`<textarea>` possèdent la fenêtre candidate IME,`compositionstart/update/end` et `selectionStart/End`.

`CanvasRenderingContext2D.fillText`écrit les pixels. Le navigateur ne peut pas les nommer, les trouver ou les copier.`find-in-page`(Ctrl+F), les liens de fragments `#:~:text=`, les extensions de traduction, le mode lecteur, les lecteurs d'écran et les robots d'exploration marchent tous dans le DOM - le canevas est invisible pour chacun d'entre eux. Toute interface utilisateur de canevas qui souhaite une sélection native doit **projeter** une couche DOM sémantique et la garder géométriquement impossible à distinguer de l'encre. Une dérive de même 0,5 px peint un reflet qui glisse visiblement de ses glyphes ; la dérive d'un caractère copie le mauvais texte ; la dérive d'un cluster de graphèmes interrompt le placement du curseur pour CJK et emoji.

L’échec est toujours géométrique – et il s’aggrave avec l’étalonnage. Même une disposition correcte par graphème dérivera si `getBoundingClientRect`est quantifié (DPR), si `style.font`est un getter (Chrome 480×) ou si le bloc contenant la superposition fait courir le compositeur (`fixed`vs `absolute`). La géométrie, la mesure et l'alignement du compositeur constituent un système et non trois. Deux mises en page qui dérivent de la même chaîne logique mais la mesurent différemment (chemin `measureText` différent, sauts de ligne différents, ordre bidi différent, taquets de tabulation différents) divergeront. La règle pour tout le texte VectoJS : **compiler une fois, consommer deux fois** — un plan géométrique conservé alimente à la fois la peinture et la projection, jamais deux mises en page indépendantes.

## 2. Les deux mondes

```text
┌──────────────────────────────────────────────────────────────────┐
│  Visual world — canvas                                           │
│  source: string ──► LayoutEngine / prepareContentGrid            │
│       │                    │                                     │
│       │  PreparedText / PreparedContentGrid (immutable, retained)│
│       ▼                    ▼                                     │
│  flushRun / per-glyph fillText / MSDF atlas ──► pixels           │
│  at world transform (a,b,c,d,e,f) × DPR × page zoom              │
└──────────────────────────────┬───────────────────────────────────┘
                               │  same source, same plan, same epoch
                               │  same font, same advances, same x/y
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│  DOM selection world — a11y / content layer                      │
│  getContentProjection() ──► ContentProjection                     │
│       │  { text, font, lineHeight, baseline, lines[], grid }     │
│       ▼                                                          │
│  Scene.syncA11y ──► per-line carriers (<span>)                   │
│       │  data-vecto-grid-cell / per-grapheme spans               │
│       ▼                                                          │
│  live DOM Range ──► Selection / copy / find / IME anchor         │
└──────────────────────────────┬───────────────────────────────────┘
                               ↕
              calibrated each frame by CanvasGeometry
              + ContentProjectionManager grid calibration
              + DPR / page zoom compensation (256 px basis)
              + font-epoch / viewport-epoch generation stamping
```

Les deux mondes dérivent d'**une source logique** (`source: string`) et d'un plan géométrique conservé. La re-segmentation de la source du DOM crée une deuxième mise en page qui est inévitablement en désaccord : différents sauts de mots sous CJK, ordre visuel bidi différent, arrêts de colonne de tabulation différents, distribution différente de la hauteur de ligne. La projection ne se renouvelle jamais ; il réutilise les propres coordonnées du moteur.

Les grilles préparées dans `packages/text/src/PreparedContentGrid.ts`et la prose dans `packages/layout/src/LayoutEngine.ts`ne diffèrent que par l'unité (cellule de grille vs CSS px) — les deux émettent `x/advance/level` par cellule/glyphe, donc le même emplacement Bidi-aware sert les deux.

La superposition qui héberge les supports est elle-même un artefact géométrique. `CanvasGeometry.syncOverlay`(`packages/core/src/tree/scene/CanvasGeometry.ts:1`) maintient les couches `a11yRoot`/`portalRoot`alignées avec la boîte CSS du canevas via `getBoundingClientRect`, y compris la distinction de bloc contenant `position: fixed`vs `absolute`qui décide si le défilement nécessite une compensation JS (§4.3). Le CSS `transform: scale(cssWidth/width, cssHeight/height)` de la superposition mappe les coordonnées logiques Scene sur la boîte CSS ; le gestionnaire de projection de contenu mappe ensuite les coordonnées de ligne logique sur cela.

## 3. Comment VectoJS le comble

### 3.1 Un forfait retenu, deux consommateurs

**Documents en prose** — `Markdown`(`packages/markdown/src/Markdown.ts`),`RichText`/`Text`(`packages/ui/src/RichText.ts`,`packages/ui/src/Text.ts`) mis en page via `LayoutEngine`(`packages/layout/src/LayoutEngine.ts:1`). Le moteur émet `LayoutResult`avec `nodes: PreparedGlyph[]`, chacun portant `x / y / width / height / sourceIndex / sourceLength / isRTL / style / object`.`RichText.buildVisualLineGroups()`(`packages/ui/src/RichText.ts:668`) regroupe les glyphes par ligne de base (`node.y + 0.8*height`), coupe `sourceText`avec `projectedSlice()`(`packages/ui/src/RichText.ts:506`) donc l'objet en ligne `alt`remplace `U+FFFC`dans le texte DOM tandis que l'arithmétique `sourceIndex`reste intacte et émet `ContentProjection.lines[]`avec `runs`,`perGraphemeCarriers`,`shapedPaint`,`lineHeight`,`baseline`,`font`. Le niveau grossier (`hint.textOnly`) renvoie `{ text, font, lineHeight }` sans lignes de construction — O(1) pour les blocs hors fenêtre. Canvas `render()` et `getContentProjection()` partagent le même objet `result` ; l'identité (`===`) est le signal d'invalidation (`packages/ui/src/RichText.ts:259`,`_lineGroupsCache`).`Markdown`fait la même chose à l'échelle du document, composant `Stack`de `RichText`blocs avec une matérialisation fermée `contentSemanticBudgetLeft`(`packages/core/src/tree/Scene.ts:600`,`DEFAULT_CONTENT_SEMANTIC_BUDGET = 256`).

**Grilles de type code** — terminaux, éditeurs, `CodeBlock`(`packages/markdown/src/markdown-code.ts`) compilés via `prepareContentGrid()`(`packages/text/src/PreparedContentGrid.ts:prepareContentGrid`). Les entrées sont `font`(raccourci CSS),`cellWidth`,`lineHeight`,`baseline`,`tabSize`. La sortie est un `PreparedContentGrid`immuable (`kind: 'content-grid'`,`revision`,`lines: PreparedContentGridLine[]`) où chaque `PreparedContentGridCell`porte `sourceStart/End`,`sourceCaretOffsets`(limites légales des graphèmes),`glyph`(en forme),`x`,`advance`,`level`(bidi). La mise en forme arabe (`ArabicShaper.ts`) et la réorganisation du bidi (`BidiResolver.ts:reorderVisual`) s'exécutent une fois ; les cellules restent dans l'ordre logique des sources avec l'ordre visuel d'encodage `x`.`Typography.cssLineBoxBaseline()`(`packages/text/src/Typography.ts:cssLineBoxBaseline`) dérive la ligne de base compatible avec le canevas à partir de `fontBoundingBoxAscent/Descent`via le contexte attaché partagé - même valeur utilisée par les deux mondes. La grille est renvoyée sous la forme `ContentProjection.grid`et réutilisée à la fois pour la peinture et la projection ; onglets, large CJK/emoji (`isWideCluster`), variation `VS15/VS16`, clusters ZWJ, niveaux bidi, propriété de la source `CR/LF/CRLF`(`nextSourceStart`) partagent un plan.

**Pourquoi conservé est important.** La re-segmentation de la source du DOM crée une deuxième mise en page. Mesuré sur `compare-pretext.ts`: le repli naïf de `0.5em` était réduit jusqu'à 50 % (japonais) tandis que VectoJS correspondait à la vérité terrain du DOM avec une erreur de décompte de lignes de 0 % lorsqu'on lui donnait des métriques réelles. Deux mises en page seront toujours en désaccord ; un seul plan élimine la question.

### 3.2 Supports par graphème - la seule granularité correcte

`Scene.syncA11y`matérialise un support invisible `<span>` par **graphème** pour la prose sélectionnable (`packages/core/src/tree/Scene.ts:760` ff,`perGraphemeCarriers` chemin). La largeur de chaque support correspond à l'avancée du graphème **isolé** à la police réelle de la ligne ; son `left` est la largeur du préfixe façonné à cet index moins le décalage logique accumulé. Pourquoi par graphème :

- Les porteuses plus grossières qu'un graphème échouent déjà parce que l'erreur intra-porteuse est le **crénage**, et non l'ajustement de la grille. Le mélange CJK+Latin à **deux** graphèmes par porteur était de −0,582 px (`vectojs-docs/KNOWN_ISSUES.md:137`). Non linéaire, par cluster, aucune correction uniforme ne peut l'absorber.
- La disposition de la grille Gecko s'adapte au DOM et avance jusqu'aux pixels entiers du périphérique tandis que le canevas `measureText`conserve les pixels fractionnaires : ~ 0,36 % par caractère, s'accumulant linéairement.`text-rendering: geometricPrecision`et désactivation du crénage/ligatures mesurées **identiques** à `auto`— pas de trappe d'évacuation CSS (`packages/text/src/measureContext.ts:34`,`KNOWN_ISSUES.md:131`). Un transporteur par graphème est le correctif expédié ;`Monospace` (avancées uniformes) est entièrement désactivé (0 dérive, pas de porteuses).
- Les porteurs sont `position: relative`+`display: inline-block`avec `left = run.x − runningLogicalX`dans l'ordre logique DOM (`packages/ui/src/RichText.ts:584`,`Scene.ts`chemin par graphème). Jamais `absolute`— il bloque les boîtes en ligne (`computed display: block`) et la sérialisation du texte brut en fonction de la mise en page est interrompue à chaque boîte de bloc :`innerText`a généré 16 nouvelles lignes contre 2 correctes, 0 espace contre 14 correctes pour le texte justifié (`KNOWN_ISSUES.md:190`). Flow-relative conserve la copie, la recherche dans la page et les lecteurs d'écran lisant une ligne comme une ligne. RTL/bidi partage ce chemin ; le visuel `x`provient des niveaux `BidiResolver`, l'ordre DOM reste logique.

L'exception est le chemin rapide de `ui/Text`: un `fillText`en forme par ligne (l'encre inclut le crénage/ligatures) déclare `ContentProjectionLine.shapedPaint = true`(`packages/ui/src/RichText.ts:shapedPaint`). Ses supports utilisent délibérément des différences de préfixes **de forme** — une peinture assortie (§4.1). Les lignes justifiées n'utilisent jamais de porteurs par graphème ; ils réutilisent la propre géométrie `positionedRuns`de la mise en page (`packages/ui/src/RichText.ts:626`).

La segmentation elle-même se fait via `Intl.Segmenter`avec `granularity: 'grapheme'`(`packages/text/src/PreparedContentGrid.ts:graphemes`,`packages/core/src/tree/Scene.ts:graphemeBoundaries`). Fallback est un segmenteur déterministe au niveau des points de code (`fallbackGraphemes`) couvrant la combinaison de marques, de sélecteurs de variations (`VS15/VS16`), de modificateurs d'emoji, de touches, d'indicateurs régionaux et de ZWJ. Monospace n'a besoin d'aucune segmentation (cellule = caractère ;`PreparedContentGrid` toujours compatible ZWJ pour les emoji dans les grilles de cellules).

### 3.3 Projection de la grille de contenu — le chemin retenu

Les supports de grille sont des travées `data-vecto-grid-cell`portant `data-vecto-grid-sourceStart/SourceLength/advance/x/level/caretOffsets/font/lineHeight`(`packages/core/src/tree/scene/ContentGridProjector.ts:291`). Ils sont:

- **Fenêtré** — uniquement les lignes proches du support de la fenêtre (`contentProjectionMargin`, indice `minY/maxY`dans `packages/core/src/tree/Scene.ts:projectedLines`). Les supports hors écran sont `display: none` et ne peuvent pas intercepter les entrées.
- **Réutilisé** (`carrier reuse`,`#244`) — un ajout diffusé réutilise les transformations `scaleX`calibrées des lignes intactes en place (`packages/core/src/tree/scene/ContentProjectionManager.ts:536`). Seules les cellules de la queue reconstruite sont en attente d'étalonnage.
- **Font-mirrored** — `ContentGridProjector`reflète la police sur `data-vecto-grid-font`afin que l'étalonnage la relise sous forme de chaîne simple sans toucher à `target.style.font`, qui dans Chrome se re-sérialise à chaque lecture (`ContentProjectionManager.ts:292`, §4.4).

La sélection dans la grille est un instantané sous forme de **décalages source** (`ContentProjectionManager.ts:snapshotGridSelection`,`gridSelectionEndpointOffset`), et non des décalages DOM linéaires.`gridSelectionEndpointOffset`marche du `Selection.anchorNode/focusNode`actif jusqu'au `sourceStart`de la cellule porteuse et ajoute le décalage local de la cellule, fixé à `sourceLength`(la rupture dure de fin réside dans le même nœud de texte mais n'appartient à aucune cellule). Les décalages de source sont stables face aux sauts de ligne, au fenêtrage et à l'étalonnage `scaleX`par cellule ; le décalage linéaire 0 signifie "première ligne actuellement matérialisée" et se déplace lorsque la fenêtre le fait.`gridCaretAtSourceOffset`résout un décalage stocké en `TextCaretPosition`en analysant `data-vecto-grid-cell` dans l'ordre logique - la première cellule couvrant gagne, la limite se résout jusqu'à la fin de la cellule précédente (même signe d'insertion).

### 3.5 Synchronisation – ne montrez jamais à l'utilisateur un DOM à moitié construit

**Par frame : matérialisation puis calibrage.** Le calibrage est un lot froid de deux frames (`ContentProjectionManager.ts:700`ff) : la frame N construit une sonde lointaine hors écran (`left: -100000px`,`width: 100000px`,`contain: layout style paint`), la frame N+1 lit `Range.getBoundingClientRect().width`et écrit `scaleX`par cellule (`element.style.transform = scaleX(...)`). Le streaming superposé de manière stable (ajout sans changement de disposition) coûte une correspondance de sélecteur `querySelectorAll`. Deux premières sorties évitent complètement la sonde :`pendingCells.length === 0`(déjà calibré,`vectoGridReady`publié à partir d'un rappel de trame, jamais de manière synchrone - les porteurs disposés plus tôt dans la même tâche distribueraient autrement des rects de largeur nulle) et `measurements.length === 0` (chaque cellule en attente était en avance nulle ou vide, estampillée immédiatement).

**Coût de lecture : une mise en page par parcours, pas par élément.** `selectionPresent()`(`ContentProjectionManager.ts:selectionPresent`) mémorise une lecture `Selection.anchorNode`dans `presentThisSync`(une mise en page forcée par parcours synchronisé).`releaseSelectionForRebuild`est rejeté à bas prix lorsqu'il n'existe ni ancre suivie ni sélection en direct - le chemin de matérialisation en masse (des centaines de blocs) ne paie aucune mise en page.`presentThisSync`est invalidé en haut de chaque parcours et effacé après toute libération ou `setBaseAndExtent`.

**Estampillage de génération.** L'époque de la police (renforcée lors du chargement de la police Web, recréation `createMeasuringContext`) plus `pageScaleX`(zoom du navigateur, base 256 px) forment la génération d'étalonnage (`ContentProjectionManager.ts:524`,`stamp = fontEpoch:pageScaleX.toFixed(4)`). Une bosse incrémente `calibrationGeneration`; chaque `scaleX`par cellule est implicitement invalide sans toucher aux supports. Les cellules portent `data-vecto-grid-calib = generation` donc la réutilisation laisse les lignes intactes.

**Le risque de reconstruction.** Le remplacement des enfants de projection alors qu'un utilisateur a une sélection dans le préfixe inchangé l'efface - un message en streaming remplace ses enfants de projection sur chaque morceau ajouté. `preserveSelectionAcrossRebuild`(`ContentProjectionManager.ts:preserveSelectionAcrossRebuild`) capture les points de terminaison sous forme de décalages de caractères linéaires (`projectionAbsoluteOffset`) pour la prose ou les décalages de source pour les grilles, saute lorsqu'un glissement de région vide est en cours (le navigateur fait autorité à mi-glisser) ou lorsque l'élément propriétaire ne contient pas la sélection, puis se résout par rapport au nouveau DOM après `rebuild()`et restaure via `Selection.setBaseAndExtent`. L'instantané `refocus`adjacent dans `A11yProjectionManager.ts:211`fait la même chose pour `document.activeElement`; La sélection n'avait pas d'équivalent jusqu'au correctif d'effondrement du streaming de `KNOWN_ISSUES.md:232`.

**Limite de virtualisation.** `contentProjectionMargin`(fini) libère des blocs entiers hors écran ;`Infinity`les maintient résidents (à ~ 137 ms par `syncA11y` à 10 000 blocs). La recherche du navigateur couvre le contenu matérialisé ; une entité virtualisée non montée ne peut pas être recherchée – une application doit conserver les cibles de recherche résidentes.

**Pourquoi le budget est de 256.** Dimensionné par rapport à deux coûts mesurés : créer un `Span`par bloc (~0,4 ms) ou terminer la marche. À 64 ans, la durée totale du mur était d'environ 6 × (ère `ContentGridPageScaleBasis.test.ts`) sans gain lié à l'image (`Scene.ts:595`). 256 est l’endroit où les deux buts s’arrêtent.

**Budget différé.** `contentSemanticBudgetLeft`(`Scene.ts:600`, 256 blocs par défaut) limite un parcours de synchronisation, de sorte qu'un document de 10 000 blocs se termine en ~ 285 passes, pas une seule image interrompue.`contentSemanticDeferred`contient le débordement ;`contentViewportEpoch`assure un redimensionnement des niveaux sans déplacer de blocs. Les porteurs de la queue différée sont grossiers (`textOnly`) jusqu'à leur passage — la géométrie de sélection est différée avec eux, ce qui est correct car un bloc hors écran ne peut pas posséder de traînée.

### 3.6 Pointeur → caret : comment un clic trouve le bon nœud Texte

Les clics commencent dans la fenêtre d'affichage (`clientX/Y`) et doivent atterrir sur un `TextCaretPosition { node: Text, offset: number }`en coordonnées logiques Scene (`Scene.ts:clientToScene` est uniquement destiné aux tests de frappe ; la projection a son propre inverse).

- **Lignes de doc en prose** (`Scene.ts:nearestOffsetForPoint`) : étant donné le nœud `Text`pour une ligne, énumérez `graphemeBoundaries()`(même `Intl.Segmenter`que §3.2), placez un `Range`réduit à chaque limite, appelez `range.getBoundingClientRect()`pour obtenir la propre boîte de glyphes du navigateur et choisissez la plus proche par `distanceToRectSquared`. Caret atterrit sur un bord de graphème légal, pas à l'intérieur d'un cluster.`distanceToRectSquared` est testé par rapport aux bords de la fenêtre, de sorte qu'un échec en dehors de la ligne se résout toujours au point de terminaison le plus proche.
- **Cellules de la grille** (`Scene.ts:gridCellCaret`,`nearestGridPositionInLine`) : les données des cellules `level/advance/x/caretOffsets`donnent les fractions visuelles et sources.`visuallyRtl = (level & 1) !== 0`retourne `visualFraction → sourceFraction`, puis `caretIndex = round(sourceFraction × (caretOffsets.length−1))`. Le mappage est compatible Bidi : le point visuel le plus à droite d'une cellule RTL est son début logique.`nearestGridPositionInLine`préfiltre les cellules par `localX ∈ [x, x+advance]` pour des frappes exactes, puis les plus proches par distance horizontale.
- **Lignes de quadrillage sous transformations affines** (`Scene.ts:clientToGridLocal`) : le chemin rapide lit trois marqueurs `data-vecto-grid-basis="origin/x/y"`placés sur la ligne 0 (`ContentGridProjector.ts:basis markers`) et récupère l'affine en inversant la base 2×2 (`determinant = xx*yy − xy*yx`). La solution de secours inverse le CSS `transform`(`parseCssMatrix`) de la racine du contenu et compense l'échelle `canvasRect → logical`pour le zoom DPR/page. Le même seuil déterminant (`1e-9`) ouvre les deux portes. Lorsque la ligne n'est pas pivotée/non mise à l'échelle (`a>0, d>0, |b|,|c| ≤1e-9`),`Scene.ts:nearestGridPosition`ignore l'inverse complet et mappe `localX = (clientX − rect.left)/scaleX` pour un chemin supplémentaire bon marché.

Tous les trois partagent un vocabulaire : `collectTextNodes`/`projectionAbsoluteOffset`/`projectionCaretAt`(`packages/core/src/tree/scene/content-caret.ts:1`). Le `affinity: 'forward' | 'backward'` de ce dernier épingle un décalage de limite au nœud de texte de début ou de fin – la différence entre restaurer une sélection à la fin de la cellule N et au début de la cellule N+1, qui est le même curseur.

### 3.7 Contrat de base : un numéro, deux équarrisseurs

Le texte du canevas et la projection de contenu doivent utiliser le même décalage de ligne de base à l'intérieur d'une zone de ligne CSS, ou chaque ligne après la première accumule une dérive verticale (mesurée ~ 0,35 em par ligne plus ~ 6 px sur la ligne 0 à 24 px, corrigée dans CTX-0333/0334).

`Typography.cssLineBoxBaseline()`(`packages/text/src/Typography.ts:cssLineBoxBaseline`) est la source unique :`baseline = (lineHeight − ascent − descent)/2 + ascent`. Trois niveaux :

1. **Toile jointe** (`getSharedMeasuringContext().measureText('Mg').fontBoundingBoxAscent/Descent`) — même police que la toile peinte (§4.2 attention détachée ;`Typography.ts:32`). LRU 512 entrées saisies `font\0lineHeight`(`BASELINE_CACHE_MAX = 512`), avec actualisation LRU en cas d'accès.
2. **Métriques enregistrées** (`getFontMetrics(family).ascenderEm/descenderEm × size`,`Typography.ts:registeredBaseline`) — lorsqu'aucun canevas n'existe encore ou en SSR, même formule de centrage afin qu'une police enregistrée et un vrai navigateur soient d'accord. Le négatif `descenderEm` est devenu positif pour correspondre à la polarité du canevas.
3. **Retour** — `lineHeight × 0.8` lorsque la famille n'a pas d'ascendant/descendant. Préserve le contrat déterministe sans DOM ; SSR et le navigateur ne sont en désaccord que sur la solution de secours, et non sur une mise en page manquante.

Chaque flux de travail qui centre les métriques de police dans une zone de ligne doit appeler ceci : `RichText.buildVisualLineGroups`,`TextEntity`,`MSDFTextEntity`(lorsque les glyphes correspondent 1:1 à la source),`ContentGridProjector`. Avant ce contrat,`TextEntity`/`MSDFTextEntity`utilisait des pitchs ad hoc `0.8em`et `(ascender−descender)em` et manquait la projection d'environ 6 px + 0,35 em/ligne dans Firefox (corrigé CTX-0333/0334).

Tous les environnements n’ont pas de canevas. Trois couches, consultées par ordre de préférence par `resolveGlyphMeasurer()`(`packages/layout/src/measure.ts:resolveGlyphMeasurer`) :

### 3.9 Streaming & fenêtrage : là où la sélection rencontre l'échelle du document

`Markdown`(`packages/markdown/src/Markdown.ts:681`) compose un `Stack`de `RichText` blocs. Deux mécanismes de fenêtrage orthogonaux interagissent avec la sélection :

- **`virtualizeBlocks`** (`MarkdownOptions.virtualize`,`Markdown.ts:614`,`virtualOverscan`par défaut 800) — blocs de niveau supérieur à proximité du support de la fenêtre d'affichage ; hauteur hors écran comme `RowHeights`(arbre Fenwick sur `height+blockGap`). Incompatible avec le streaming (`createStream`/`appendMarkdown`) : un document qui se virtualise doit être rendu entier. L’appelant pilote `setVisibleRange`à chaque image de défilement (un `ScrollView` le fait automatiquement).
- **`tableViewportHeight`** (`MarkdownOptions.tableViewportHeight`,`Markdown.ts:652`) — virtualisation de ligne par table (`Table`virtualise ses propres lignes en un `viewportHeight`fixe). Indépendant du fenêtrage des blocs ; fonctionne à mi-parcours car `Table.appendRows`se monte paresseusement. S'applique à toutes les tables, y compris les tables courtes — une table à deux rangées est également fixée à cette hauteur, par construction (Table prend `viewportHeight`comme `readonly`).

`Markdown.streamStats`(`Markdown.ts:951`) — compteurs bon marché toujours actifs — distinguez le **transfert** (`tokensPrefixMatched`/`tokensReturned`) du **coût de l'analyseur** (`lexerMs`/`sourceCharsLexed`). L'ancienne dénomination les confondait, envoyant les lecteurs optimiser le chemin delta déjà résolu. Le `incrementalLex`du travailleur ignore le préfixe stable ; les formes dégradées (deux cas `DegradeReason`) paient toujours O (document) par ajout — la longueur du document de suivi `sourceCharsLexed`est le signal.`stablePrefixChars`est expédié par le propre `IncrementalLexCache.stableOffset` du travailleur, non récapitulé par réponse (qui était O(n²) sur un flux de n morceaux, #657).

`CodeBlock`(`packages/markdown/src/markdown-code.ts`) et les mathématiques d'affichage (`MathBlock`,`packages/markdown/src/markdown-math.ts`) ne sont **pas** des moteurs de rendu de blocs clôturés de registre (`Markdown.ts:138`). Le registre reçoit `(source, lang, options)` mais les deux chemins nécessitent un état d'instance -`subscribeInlineMathRepaint` et `subscribeInlineMathRaster`/`subscribeInlineImageRaster`pour les scènes `onDemand`, plus l'objet unique `RichText`qui permet à une formule d'atteindre la sélection/recherche/copie. Les copies de registre ont divergé silencieusement (`MathBlock`construit comme `(mathRender, source, ...)` lorsque la signature est `(formula, svgUri)`), brisant 7 tests (`Markdown.ts:154`). Le registre est un point d'extension pour les langues que le package n'implémente pas.

Pertinence de la copie : une cellule `Table`est projetée par cellule ; une grille `CodeBlock`utilise `PreparedContentGrid`; une formule `MathBlock`est un texte projeté plus un nom accessible ; chacun participe à la recherche/sélection uniquement lorsqu’il est matérialisé. La copie du presse-papiers pour une sélection couvrant plusieurs blocs est la concaténation de `projectedSlice` par bloc - la substitution alt SVG/Math en ligne selon §3.1 conserve les décalages intacts.

### 3.10 Bases de référence et pourquoi elles existent

`forge/baselines/*`et `vectojs-docs/forge/baselines/*`épinglent les nombres cités par ce document afin qu'un changement futur puisse être divisé en deux plutôt que remesuré à partir de ouï-dire. Concrètement : la table de base de 256 px (1/2/4/10/100/1000 px → 0.9921875…1.0), le triple `measureText('MMMMMMMMMM')`détaché contre attaché pour `monospace/serif/sans-serif`sur Firefox (`measureContext.ts:1`), le désalignement défilement/rendu de 64,8 px (défilement lisse de 661 images / 630 px), le Coût du getter `style.font`de 288/290 ms (Chrome contre 0,6 ms Firefox) et taux de réussite des mémos de bloc `Stack`+`RichText`(0 → 2388 après `EMPTY_GLYPH_ATLAS`).`KNOWN_ISSUES.md`enregistre le rejet par graphème (deux graphèmes → −0,582 px sur CJK+Latin mixte) et l'échec du texte en clair du support `absolute`(16 nouvelles lignes contre 2, 0 espaces contre 14). Lorsqu'un nouveau moteur ou hôte signale un écart différent, réexécutez le harnais au niveau du `DPR/ZOOM`épinglé et comparez-le avec la validation de base - la différence est de savoir si le correctif est un bug de la visionneuse ou une régression VectoJS.`packages/core/test/ContentGridPageScaleBasis.test.ts`est le seul oracle au niveau unité pour la quantification ; tout le reste nécessite un navigateur dirigé (COOP/COEP pour la fidélité `performance.now`, fenêtre ciblée pour les rappels du compositeur — voir la compétence `vectojs-performance`).

## 4. Pièces dures — avec reçus

### 4.1 Dérive de crénage : avancées sur une chaîne entière ou isolée

La mise en page positionne les glyphes en additionnant **isolé** par graphème `measureText(char).width`(`packages/layout/src/measure.ts:createCanvasMeasurer`→`getSharedMeasuringContext()`,`baseSize 100`mis à l'échelle arithmétiquement). La peinture reste à moins de 0,5 px de la mise en page (`packages/ui/src/RichText.ts:COALESCE_TOLERANCE_PX`) —`flushRun`fusionne une course en un seul `fillText`uniquement lorsque `abs(measureText(runText) − sum(isolated)) ≤ 0.5`(`RichText.ts:1001`), sinon revient aux dessins par caractère à `node.x`. La chaîne entière `measureText(text).width`inclut le crénage de la toile, jamais peinte. Les supports qui utilisaient des largeurs de chaîne entière étaient donc **en avance sur l'encre par le delta de crénage accumulé**, jusqu'à 5 à 8 px sur une ligne latine de 16 px avec un crénage d'environ 300 px, à la fois Gecko et Blink (`KNOWN_ISSUES.md:168`).

Correctif : les largeurs des supports suivent le modèle de peinture de la ligne via `ContentProjectionLine.shapedPaint`. Les peintres par glyphe (`RichText`, noyau `TextEntity`) obtiennent des avancées en graphème isolées ; Le chemin rapide de `ui/Text`(un `fillText`en forme par ligne) déclare `shapedPaint`et conserve les porteurs de différence de préfixe en forme. Les lignes justifiées réutilisent la propre géométrie `positionedRuns`de la mise en page et n'ont jamais eu cette dérive.`logicalRuns`additionne les avancées isolées via `mctx.measureText(segment)`(`RichText.ts:598`) ;`positionedRuns`réutilise `node.x/width`directement. Le chemin par graphème dans `Scene.ts` reflète cette branche.

Un correctif frère : `RichText.logicalRuns`utilisait auparavant la mesure de chaîne entière par exécution ; Le chemin par graphème de `Scene`mesurait les différences de forme des préfixes — même classe, même correctif (PR #460,`@vectojs/core@1.35.1`+`@vectojs/ui@2.16.3`).

### 4.2 Quantification DPR et base d'échelle de page de 256 px

Les navigateurs arrondissent `getBoundingClientRect().left`à **1/64 px de l'appareil** (`ContentProjectionManager.ts:62`,`CanvasGeometry.ts:PAGE_SCALE_BASIS_PX`). Une sonde de 1 px quantifie à un multiple de 1/64 ; dans DPR 1.1, l'échelle des pages récupérées était de **0,9921875** (=63,5/64) où vrai était de 1,0 — une erreur de 0,78 % (`ContentProjectionManager.ts:68`). Chaque `scaleX = advance * scale / natural`(`ContentProjectionManager.ts:717`) par cellule a diminué de ce facteur : pas de 18,0001 px sélectionné à 17,8624 px, laissant un écart de **0,133 px** à chaque couture CJK et 0,061 px à chaque couture latine ; dans DPR 1.1, ceux-ci atterrissent sur une limite appareil-pixel et sont peints sous la forme d'une ligne blanche verticale `使|用|sudo`(`ContentProjectionManager.ts:71`). Measured over bases 1/2/4/10/100/1000 px on the same page:`0.9921875, 1.0, 0.998046875, 1.0, 1.0, 1.0` — chaque base ≥10 px est exactement convenue ; la lecture de 1 px était la valeur aberrante.

Correctif : mesurez plus de **256 px** (`PAGE_SCALE_BASIS_PX = 256`,`ContentProjectionManager.ts:85`). Le pire des cas devient `1/64 / 256 = 6.1e-5`(résidu de 0,0011 px sur 18 px, ~ 100 × en dessous d'un pixel représentable par le navigateur) tout en restant loin à l'intérieur de la largeur de 100 000 px de la sonde afin qu'elle ne puisse pas introduire de barre de défilement ou sa propre mise en page (`ContentProjectionManager.ts:80`). Oracle de test :`packages/core/test/ContentGridPageScaleBasis.test.ts` modélise directement la quantification.

Frère : les canevas de mesure détachés résolvent les erreurs des familles génériques sur Firefox (`packages/text/src/measureContext.ts:1`).`22px monospace`détaché 109,737 contre 131,579 attaché contre 132,000 mise en page ;`serif`détaché s'est effondré sur le repli de `monospace`(−47 % sur `serif`, -20 % sur `monospace`). Seul `sans-serif`était d'accord, c'est pourquoi les tests Chromium uniquement l'ont masqué. Chaque mesureur doit utiliser `getSharedMeasuringContext()`(ci-joint,`document.body`-parenté, jamais `display: none`).`OffscreenCanvas` mesure correctement (132 000) mais le contrat est "mesurez là où vous peignez" — la toile peinte est attachée, donc celle qui mesure doit l'être aussi. L'écart résiduel d'environ 0,3 % entre l'attachement et la mise en page est l'ajustement de la grille Gecko du §4.4, pas celui-ci.

### 4.3 Compositeur vs thread principal vs dérive fixe/absolue

Un canevas à fenêtre complète `position: fixed`est composé par rapport à la fenêtre **hors du thread principal** ; une superposition `absolute`est disposée sur le document défilant. Les garder ensemble en redérivant `top`de `parent.getBoundingClientRect()`par image **rendue** a laissé la superposition obsolète à chaque fois que le défilement avançait sans rendu. Mesuré sur une scène en direct avec fenêtre complète, véritable défilement fluide piloté par touche sur 630 px : 661 images échantillonnées, **1 image mal alignée de 64,8 px** (`CanvasGeometry.ts:191`).

Correctif : la superposition hérite du propre `position`(`CanvasGeometry.ts:206`,`getComputedStyle(canvas).position`) du canevas.`fixed`résout `left/top`par rapport à la fenêtre - exactement `canvasRect.left/top`(`CanvasGeometry.ts:222`) ;`absolute`conserve l'arithmétique relative aux parents avec `clientLeft/scrollLeft`(`CanvasGeometry.ts:226`). Scroll n’a alors besoin d’aucune compensation JS ; le correctif **supprime** la dépendance par image plutôt que de synchroniser plus souvent. Un auditeur de défilement utiliserait toujours le compositeur en tant que travail de fil principal. Les écritures restantes sont mémorisées (`OverlayGeometry: left/top/cssWidth/cssHeight/width/height/position`,`CanvasGeometry.ts:235`), donc un cadre inchangé n'écrit rien - des affectations identiques touchent toujours le CSSOM et augmentent avec le nombre de couches de superposition (`CanvasGeometry.ts:250`).

### 4.4 Lacunes sous-pixels CJK et coût de recherche de police

Après la correction de l'échelle, la dérive résiduelle correspond à l'ajustement de la grille Gecko d'environ 0,36 % (la mise en page s'aligne sur un périphérique entier px, le canevas reste fractionnaire) - `text-rendering: geometricPrecision`n'est **pas** un correctif, mesuré de manière identique à `auto`(`packages/text/src/measureContext.ts:34`,`KNOWN_ISSUES.md:131`). La même classe de surprise a produit un deuxième piège de performances indépendant :`style.font`est un getter de raccourcis en direct qui resérialise chaque police longue à chaque lecture. L'analyse d'étalonnage qui indiquait `target.style.font`une fois par cellule payait **288 ms sur 290 ms (99,3 %)** dans Chrome tandis que Firefox passait 0,6 ms sur la boucle identique — un écart inter-moteur de 480 × dont le seul signal était le moteur, pas le travail (`ContentProjectionManager.ts:292`). Correctif : les opérateurs stockent une simple chaîne `data-vecto-grid-font`(`ContentGridProjector.ts:291`) et `ContentProjectionManager`la lit.`contain: layout style paint` sur la sonde l'isole.

### 4.5 IME, presse-papiers et miroir modifiable

`Input`/`TextArea`ne sont **pas** des projections de contenu. Ils projettent un véritable `<input>`/`<textarea>` transparent (`Site:Accessibility & Automation`§Champs de saisie compatibles IME,`packages/core/src/tree/Scene.ts:a11y input mirror`,`packages/ui/src/Input.ts`/`TextArea.ts`). Le navigateur possède la fenêtre du candidat IME ; le canevas reflète `value/selectionStart/selectionEnd/composition`des événements `input`/`change`/`compositionstart/compositionupdate/compositionend`du nœud fantôme et dessine le curseur, la surbrillance de la sélection et le soulignement IME par image. Le nœud d'ombre est dimensionné via `textInputStyle: { font, lineHeight, padding }`à partir de `Entity.getA11yAttributes()`→`Scene`l'applique avec `box-sizing: border-box`tandis que le canevas s'appuie sur le même remplissage et `Typography.cssLineBoxBaseline` — une ligne de base, deux consommateurs, pas de dérive verticale entre l'éditeur invisible et son miroir d'encre.

Pendant le focus, `Scene`évite de réécrire le même `value`synchronisé par l'utilisateur (suppression d'écho) : si l'état de l'application fournit une valeur véritablement différente, il est appliqué, mais un composant contrôlé qui remplace le texte doit conserver `selectionStart/End`intentionnellement, sinon le curseur saute.`Input`est une entité compatible `a11yFullViewport`sur une seule ligne ;`TextArea`est un scroller multiligne compatible `clipChildren`avec `scrollLeft`/`scrollTop` reflété sur le canevas - le même chemin de transformation du monde → superposition que toute autre entité, donc DPR/zoom/rotation s'appliquent de manière identique.

Chemin du Presse-papiers : `cut/copy/paste`et `undo/redo`sont natifs, via ce nœud fantôme, pour les champs modifiables. Pour le texte sélectionnable statique,`copy`est la propre sérialisation du navigateur de la couche projetée :`projectedSlice()`(`packages/ui/src/RichText.ts:506`) remplace le `alt`de chaque objet en ligne par la sentinelle `U+FFFC`dans l'espace **source** afin que l'arithmétique `LayoutNode.sourceIndex`reste intacte - un `alt`de n'importe quelle longueur autre qu'un, autrement, décalerait chaque décalage ultérieur et désynchroniserait les cases de sélection. Le frère `accessibleText()`(`RichText.ts:478`) existe pour le chemin `aria-label`et n'est délibérément pas utilisé pour le découpage.`SeparatorAfter`(nouvelle ligne logique/séparateur soft-wrap préservé,`ContentProjectionLine.separatorAfter`) est fusionné dans le nœud de texte final de la ligne afin que Firefox ne puisse pas placer une partie d'une sélection multiligne à la racine de projection. La copie de cellule `Table`, la copie de grille `CodeBlock`et la copie de formule `MathBlock`transitent toutes par la même concaténation `projectedSlice`par bloc — la substitution SVG/Math `alt` en ligne selon §3.1 maintient les décalages intacts à travers les limites des blocs.

Mise en garde : `packages/devtools/src/selectionAudit.ts:119`a précédemment capturé `getSelection()`, puis appelé `removeAllRanges`(`:157`) - un audit qui a détruit l'état de l'utilisateur. L'audit actuel (`selectionAudit.ts:102`) utilise `Range`détaché (`document.createRange()`+`selectNodeContents`+`getClientRects`) qui ne touche jamais `DocumentSelection` ; il n'y a pas de sélection programmatique à nettoyer. Laissez la sélection de l'utilisateur exactement telle qu'elle a été trouvée.

### 4.6 Graphème, crénage et espace blanc CJK — le bug qui ressemble à un artefact de rendu

Le `使|用|sudo` se lit comme un bug GPU : une ligne blanche verticale entre les glyphes Han adjacents. Il s'agit d'un bug de sélection-projection visible à travers le raster. La chaîne est :

1. `getBoundingClientRect().left`quantifié à 1/64 px de l'appareil sur une base de 1 px →`basisScale`0,78 % faible à DPR 1.1 (`ContentProjectionManager.ts:68`) ;
2. `scaleX = advance × basisScale / natural`0,78 % faible (`:717` );
3. chaque `data-vecto-grid-cell`peint `advance`large mais boîte de sélection dimensionnée à partir de `advance × scaleX`→ chaque couture CJK 0,133 px courte (`:71`) ;
4. dans DPR 1.1, le déficit atterrit exactement sur une limite appareil-pixel → le compositeur laisse une colonne découverte → blanche.

Les coutures latines ont la même géométrie (0,061 px) mais `advance`plus étroite la cache. Changer le rastériseur, passer à `geometricPrecision`ou désactiver le crénage ne fait rien - l'espace n'est pas dans l'encre mais dans le `scaleX`avec lequel l'encre est dessinée. Le test qui le protège est l'oracle de base à l'échelle de la page (`ContentGridPageScaleBasis.test.ts`) plus le harnais à tête de `DPR=1.1` ; le DPR 1 sans tête ne reproduit rien.

### 4.7 L'étalonnage n'est pas une solution ponctuelle : la police, le DPR et la fenêtre d'affichage forcent chacun un ré-estampillage

Le `scaleX`par cellule est `advance × (pageScale × deviceScale) / natural`uniquement au moment où il a été mesuré. L'une des trois entrées peut changer sans que l'entité ne bouge : une police Web se termine (bump `contentFontEpoch`,`watchFontMetrics`→ époque,`Typography.clearCssLineBoxMetrics`), l'utilisateur effectue un zoom (échelle de page via `getBoundingClientRect`sur une base de 256 px,`ContentProjectionManager.ts:524`) ou `devicePixelRatio`/ changements de taille du canevas (`Scene.resize`→`CanvasGeometry.effectiveDPR`→`contentViewportEpoch`).`calibrationGeneration`(`ContentProjectionManager.ts:calibrationGeneration`) les regroupe en un seul compteur afin qu'une seule comparaison invalide chaque cellule. L'échec lorsque cela est manqué est silencieux : l'ancien `scaleX`reste, les porteuses sont à la mauvaise largeur et `selectionAudit`signale une dérive qui augmente avec la longueur de la ligne mais disparaît lors de l'actualisation.`data-vecto-grid-calib`est le champ à surveiller — toute cellule estampillée `generation` qui survit à un zoom est une lecture obsolète.

### 4.8 Comment l'exactitude est réellement mesurée : le harnais de sélection

Headless (`jsdom`,`--disable-gpu`) n'a pas de GPU, pas de compositeur, pas de géométrie `Range`en DPR fractionnaire et `performance.now()`grossi à 100 µs sans COOP/COEP — il ne peut pas citer la parité de sélection. Seuls `scripts/selection-harness/harness.ts`+`drive.sh`le peuvent.`harness.ts`crée un véritable document `Scene`+`Markdown`+`CodeBlock`avec une source connue, une police,`maxWidth`, puis `drive.sh`lance un **vrai chef** Chrome et Firefox sur un espace de travail Hyprland dédié à `DPR`× `ZOOM`(`--force-device-scale-factor`,`layout.css.devPixelsPerPx`,`scripts/selection-harness/drive.sh:6`) et pilote un natif faites glisser via le même chemin `clientToGridLocal`/`nearestOffsetForPoint`que l'utilisateur atteint.`selectionAudit.ts:1`est l'oracle :`expectedLeft/Right`de la géométrie `ContentProjectionLine`vs `actualLeft/Right`du DOM en direct `Range`en **px logique local** (DPR/zoom divisé). Tableau vide = chaque zone de sélection suit ses glyphes ; toute découverte porte `entityId`,`entityPath`,`line`,`leftDrift/rightDrift` pour la bissection.

Trois modes de défaillance pour lesquels le harnais est conçu : espaces justifiés entre les mots, réorganisation visuelle RTL/bidi + épinglage `dir="ltr"`et arrondi DPR/zoom fractionné (`scripts/selection-harness/README.md:8`). Headless DPR 1 masque les bogues de quantification de 256 px et l'ajustement de grille Gecko d'environ 0,36 % fournis avec DPR 1.1/1.6 – exécutez le harnais à `DPR=1.5 ZOOM=0.9` ainsi qu'à 1× avant de revendiquer la parité.

## 5. Les invariants que les développeurs doivent conserver

> Chaque invariant est un endroit où deux chemins de code doivent s'accorder sur un nombre et une direction. S'ils ne sont pas d'accord, l'utilisateur voit un espace, une surbrillance décalée ou une sélection perdue – et les passes sans tête le cachent. Le `file:line` est l'endroit à vérifier, pas une suggestion.

1. **Mesurez où vous peignez.** Utilisez `getSharedMeasuringContext()`(`packages/text/src/measureContext.ts`) — ci-joint,`document.body`-parenté,`opacity: 0`à `left: -9999px`, jamais `display: none`. Jamais une toile détachée pour des familles génériques ; ne mesurez jamais à nouveau `serif`/`monospace`sans le contexte de style du document.`fontMetrics.ts`(`packages/text/src/fontMetrics.ts:registerFontMetrics`,`registerMSDFFontMetrics`) est la solution de secours sans DOM (MSDFAtlas `advance`/`kerning`/`ascender/descender`), et non le chemin préféré dans un navigateur. Après le chargement d'une police Web, appelez `clearCssLineBoxMetrics()`et laissez `watchFontMetrics` modifier l'époque - les avancées obsolètes mises en cache sont une erreur de largeur de ligne avant qu'une projection ne soit impliquée.
2. **Un plan, deux consommateurs.** Entités de type code : `prepareContentGrid()`une fois → même objet immuable pour la peinture et `getContentProjection().grid`(`packages/text/src/PreparedContentGrid.ts`). Prose :`LayoutEngine`une fois → même `LayoutResult`pour `render()`et `getContentProjection()`(`packages/layout/src/LayoutEngine.ts`,`packages/ui/src/RichText.ts:284`cache). Ne jamais re-segmenter, réemballer ou re-tokéniser pour le DOM.`EMPTY_GLYPH_ATLAS`comme identité de l'atlas (`LayoutEngine.ts:EMPTY_GLYPH_ATLAS`) garde le mémo de paragraphe chaud.
3. **Porteurs relatifs Flow, dans l'ordre logique DOM.** `position: relative`+`display: inline-block`avec `left = run.x − runningLogicalX`(`packages/ui/src/RichText.ts:584`). Jamais `absolute`- il bloque et interrompt le texte en clair `innerText`/`textContent`, la continuité de la ligne `find-in-page`et l'itération de la ligne du lecteur d'écran. RTL/bidi partage ce chemin ; le visuel `x`vient des niveaux, l'ordre DOM reste logique donc `innerText`copie dans l'ordre des sources.`contain: layout style paint` sur la sonde, pas sur les supports.
4. **Ne tuez jamais les porteurs pour une taille d'arbre de 11y.** Les nœuds `StaticText`par caractère lisent lettre par lettre (voir `xuepoo-blog/src/text-utils.ts`) ; la désactivation des opérateurs restaure une dérive d'environ 2 px dans Firefox. Le coût de l'arbre est réel (voir `Site:Accessibility & Automation`§Le coût évolue de manière super-linéaire : 6,4 µs → 136,9 µs/entité à 20 000), mais les porteuses ne sont pas le levier : le fenêtrage (`contentProjectionMargin`) et `a11yProjection: 'onDemand'` le sont.
5. **Les décalages source sont les seules coordonnées de sélection stables.** Les décalages linéaires du DOM dérivent lorsque la fenêtre de la grille ou les sauts de ligne changent (`ContentProjectionManager.ts:gridSelectionEndpointOffset`). Grilles d'instantanés au format `sourceStart + withinCell`, prose via `projectionAbsoluteOffset`/`projectionCaretAt`(`packages/core/src/tree/scene/content-caret.ts`). L'affinité `forward`vs `backward` décide de quel côté de la limite d'une cellule un curseur s'épingle.
6. **Respectez le modèle de peinture.** `ContentProjectionLine.shapedPaint`indique à `Scene`quelle avance utiliser ; les lignes justifiées réutilisent la propre géométrie des glyphes de la mise en page (`positionedRuns`,`packages/ui/src/RichText.ts:626`). La définition de `x`sur une exécution à flux naturel inverse `hasPositionedRuns`et force `dir="ltr"`— correct pour justifier/RTL, incorrect pour un LTR irrégulier (`RichText.ts:533`). Une ligne irrégulière doit conserver `dir="auto"` pour que le navigateur bidise le texte lui-même et que le mappage des touches d'insertion reste correct.
7. **Hériter de la position de superposition.** `CanvasGeometry.syncOverlay`(`packages/core/src/tree/scene/CanvasGeometry.ts:206`) doit refléter `fixed`/`absolute`— ne redérivez pas `top`du parent par image. Mémo `OverlayGeometry`et `invalidateOverlay()`uniquement lorsqu'un nouveau calque (`glCanvas`/`gpuCanvas`/`portalRoot`) apparaît.
8. **Tampon de génération, ne balayez pas.** Les modifications de police et de zoom invalident tous les `scaleX`via un compteur de génération (`ContentProjectionManager.ts:calibrationGeneration`,`calibrationStamp = fontEpoch:pageScaleX`) ; ne touchez pas à tous les transporteurs lors d'un changement d'époque. Les cellules portent `data-vecto-grid-calib` donc la réutilisation laisse les lignes intactes.
9. **Préserver la sélection lors des reconstructions, mais pas à mi-parcours.** `preserveSelectionAcrossRebuild`/`snapshotGridSelection`+`restoreGridSelection`couvrent le risque de reconstruction en continu ; Les glissements de régions vides font autorité sur le navigateur et ne doivent pas être interrompus.`releaseSelectionForRebuild`est le frère le moins cher lorsque le texte sélectionné n'est plus projeté (la fenêtre défile devant lui - laissez le `Range` détaché plutôt que de pointer vers des supports détachés).
10. **Une ligne de base, les deux mondes.** Chaque zone de ligne (canevas et DOM) appelle `Typography.cssLineBoxBaseline()`(`packages/text/src/Typography.ts:cssLineBoxBaseline`). Ne codez jamais en dur `0.8 * lineHeight` en dehors du niveau de secours ; cette constante est la solution de repli, pas le contrat.
11. **Ne mesurez pas le mesureur.** `style.font`est un getter en direct (`ContentProjectionManager.ts:292`) ; lire `data-vecto-grid-font`. De même,`getBoundingClientRect`force la mise en page - regroupez-le (chemin de la sonde) et mémorisez-le (`selectionPresent`/`OverlayGeometry`), ne lisez pas par élément par image.
12. **La virtualisation est facultative et exclusive.** `Markdown.virtualize`et le streaming `createStream`ne composent pas (`Markdown.ts:614`) ;`tableViewportHeight`fait (`:652`). Placez les blocs critiques à la recherche dans la fenêtre montée, sinon ils seront introuvables - la matérialisation, et non la profondeur de l'arborescence DOM, décide de ce que Ctrl+F peut voir.

### 6.3 Combien coûtent les sondes – ne transformez pas un contrôle en régression

- `auditSceneSelection`appelle lui-même `getBoundingClientRect` par ligne (forçage de la mise en page) et doit s'exécuter sur un vrai navigateur, pas dans une boucle chaude. Ne l'expédiez pas sur le chemin du cadre - portez-le sur une bascule d'assurance qualité ou un harnais Playwright.
- `scene.getA11yTree()`parcourt le sous-arbre a11y ; il est commandé par `A11yProjectionManager.enforceA11yDomOrder` et stable pour les assertions mais pas gratuit sur des milliers d'entités interactives (voir tableau des coûts §5.4 : 715 ms @ 20k sur Chrome). Instantané une fois par vérification, et non par image.
- `selectionPresent()`(`ContentProjectionManager.ts:selectionPresent`) est l'exemple de production de regroupement par lots de la même lecture : une mise en page forcée par parcours de synchronisation, et non par élément. Copiez ce modèle pour tout nouveau contrôle de santé de projection.

## 7. Le plein format – six étapes, dans l'ordre

Pour une trame qui étend un bloc de code de streaming d'une ligne alors que l'utilisateur dispose d'une sélection dans le préfixe inchangé dans DPR 1.6 :

1. **Mise en page** — `prepareContentGrid`ou `LayoutEngine.layoutPrepared`émet le nouveau plan ;`Stack`remesure uniquement le bloc sale (`updateTokens`/`virtualHeights` Fenwick).
2. **Dessin sur toile** — `Scene.render`parcourt le VMT, applique `worldTransform × DPR`, émet des lots `fillText`/`drawImage`. Décision `flushRun`(`COALESCE_TOLERANCE_PX`) déjà cuite.
3. **Synchronisation de superposition** — `CanvasGeometry.syncOverlay`aligne `a11yRoot`sur `canvasRect`, héritant de `fixed`/`absolute`(`CanvasGeometry.ts:206`), mémo (`OverlayGeometry`).
4. **Matérialisation** — `syncA11y`/`syncContentProjection`dirty-check `ContentSyncState`(matrice mondiale,`hasBand`/`visible`,`fontEpoch`/`viewportEpoch`,`tier`), supports de fenêtre pour `hint.minY/maxY`, réutiliser les lignes de grille intactes `scaleX`, créer des travées par graphème ou `data-vecto-grid-cell`avec `sourceStart/Length/x/advance/level/caretOffsets`.
5. **Préservation de la sélection** — `ContentProjectionManager.snapshotGridSelection`comme décalage de source,`preserveSelectionAcrossRebuild`/`restoreGridSelection`après `rebuild()`, ou `releaseSelectionForRebuild` si le texte sélectionné défile. Le déplacement dans une région vide reste piloté par le navigateur.
6. **Calibration (à froid)** — l'image N construit la sonde de 100 000 px hors écran ; le cadre N+1 lit les largeurs naturelles `Range`, calcule `scaleX = advance × basisScale / natural`avec `basisScale`à partir de la base d'échelle de page de 256 px (`ContentProjectionManager.ts:707`), écrit `transform`, tamponne `data-vecto-grid-calib`. L'état d'équilibre est une correspondance de sélecteur ;`vectoGridReady` publié à partir d'un rappel de frame.

Toute étape qui remesure sans passer par l'étape 1 crée un deuxième tracé et une dérive future. Toute étape qui lit `style.font`ou `getBoundingClientRect` sans passer par le chemin mémo/attribut paie le coût de 480 × / mise en page par élément du §4.
