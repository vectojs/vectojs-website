# 왜 VectoJS인가

브라우저 DOM은 강력한 범용 문서 렌더러입니다. 텍스트 흐름, SEO 콘텐츠, 네이티브 폼, 적당한 수준의 상호작용 UI에 탁월합니다.

하지만 인터페이스가 문서보다는 씬(scene)에 가깝게 동작할 때 DOM은 병목 지점이 됩니다.

## 문제

VectoJS는 다음과 같은 인터페이스를 대상으로 합니다:

- 수천 개의 개별 애니메이션 항목이 과도한 DOM/스타일/레이아웃 작업을 유발하는 경우;
- 레이아웃이 CSS 흐름이 아닌 수학에 의해 제어되는 경우;
- 히트 테스트가 사용자 정의 변환, 곡선, 좌표계와 일치해야 하는 경우;
- 동일한 UI가 canvas, WebGL, 내보내기, WebXR 컨텍스트에서 실행되어야 하는 경우;
- 시각적 UI가 canvas로 렌더링되더라도 접근성과 자동화가 여전히 중요한 경우.

## 일반적인 canvas 라이브러리와의 차이점

대부분의 canvas 라이브러리는 그리기 프리미티브만 제공하고 레이아웃, 이벤트, 텍스트, 접근성은 애플리케이션에 맡깁니다. VectoJS는 보다 완전한 런타임 스택을 제공합니다.

| 계층        | VectoJS                                        | 일반적인 canvas 라이브러리 |
| ----------- | ---------------------------------------------- | -------------------------- |
| 레이아웃    | 엔티티 트리 및 레이아웃 헬퍼                   | 수동                       |
| 히트 테스트 | 엔티티별 히트 테스트 및 변환 변환              | 수동                       |
| 이벤트      | DOM 스타일의 캡처 및 버블 단계                 | 수동/콜백 전용             |
| 접근성      | 적격 엔티티를 위한 시맨틱 DOM 투영             | 보통 없음                  |
| 텍스트      | 레이아웃 엔진, 줄바꿈, BiDi, 아랍어, MSDF 경로 | `fillText`만 제공하는 경우 |
| 컴포넌트    | 폼, 오버레이, 마크다운, 스크롤, 레이아웃       | 보통 앱에서 직접 구현      |
| 내보내기    | 고정-스텝 비디오 내보내기                      | 보통 외부 도구             |

## VectoJS가 포기하는 것

VectoJS는 CSS의 편리함을 명시적 제어와 맞바꿉니다. 레이아웃과 상호작용 모델을 더 많이 직접 관리해야 합니다:

- CSS는 개별 canvas 엔티티의 위치를 지정하지 않습니다.
- 임의의 렌더링된 텍스트에 대한 네이티브 텍스트 선택이 자동으로 제공되지 않습니다.
- SEO 크롤러는 canvas로 렌더링된 콘텐츠를 페이지 텍스트로 인식하지 못합니다.
- 접근성은 투영을 통해 가능하지만, 올바른 레이블, 역할, 키보드 동작, 명암비, 보조 기술 테스트가 여전히 필요합니다.
- 엔티티 탐색, 업데이트, 시맨틱 동기화, 앱 연산은 여전히 CPU를 소비하며, canvas가 모든 작업을 무료로 만들지는 않습니다.

## VectoJS를 사용하지 말아야 할 경우

다음 상황에서는 VectoJS를 먼저 고려하지 마세요:

- 블로그, 마케팅 페이지, 문서 사이트, CMS 페이지를 구축 중인 경우;
- UI가 대부분 일반적인 폼과 테이블로 구성된 경우;
- 렌더링된 콘텐츠의 SEO 가시성이 필수 요구사항인 경우;
- 네이티브 브라우저 텍스트 선택이 제품의 핵심 기능인 경우;
- 맞춤형 레이아웃 수학, 고밀도 애니메이션, 그래프, 게임, 시뮬레이션, 또는 대규모 엔티티 씬이 없는 경우.

VectoJS는 **canvas-수준의 시각적 제어**와 함께 레이아웃, 이벤트, 텍스트, 접근성, 내보내기를 직접 구현하지 않아도 되는 충분한 런타임 인프라가 필요할 때 빛을 발합니다.
