# クロス環境の一貫性

DOMアプリはブラウザのレイアウトエンジンから一貫性（および非一貫性）を継承します。キャンバスネイティブアプリは**あなた**から一貫性を継承します：エンジンは自身が測定した数値からすべての位置を計算するため、障害モードが変化します——CSSの癖から、ピクセル密度、ズーム、フォントメトリクスへと移行します。このページは、各環境変数を、実際に何が変わるのか、エンジンがすでに何を処理しているのか、アプリケーションが何をしなければならないのかにマッピングします。

## デバイスピクセル比（HiDPI）

**エンジンが処理するもの。** すべてのVectoJS座標は論理CSSピクセルです。レンダラーはキャンバスのバッキングストアを`logical × devicePixelRatio`にサイズ設定し、コンテキストをスケーリングします。`scene.resize()`が呼ばれるたびに現在のDPRが再読み取りされます——レンダリング、hit-testing、レイアウトはすべて、分数DPR（Windows 125%/150%スケーリング）を含むあらゆる密度で、1つの論理座標空間を共有します。

**あなたがしなければならないこと。** ランタイムでは何も必要ありません——しかしテストではすべてが必要です：

> [!WARNING]
> ヘッドレスブラウザはデフォルトで`deviceScaleFactor: 1`です。ほとんどの実機はDPR 2（または分数値）です。DPRとともにスケーリングするhit-testingやテキスト投影のオフセットは、デフォルトのヘッドレス実行では**見えず**、最初の実機のラップトップで明らかになります。報告されたオフセットが原点からの距離に比例している場合は、まずDPRを疑ってください。

`deviceScaleFactor: 2`と1の両方でポインターと選択テストを実行してください（Puppeteer/Playwrightはどちらもコンテキストごとにこれを公開しています）。1つのマトリックスセルでバグのクラス全体を捕捉できます。

## ブラウザのズームとコンテナのサイズ変更

ズームは、実効DPRとCSSビューポートの両方を同時に変更します。次に何が起こるかは、誰がキャンバスサイズを所有しているかに依存します：

- **フルスクリーンシーン（デフォルト）：** Sceneはwindowの`resize`イベントをリッスンし——ズームはこれを発生させます——サイズ、バッキングストア、DPRを自動的に再調整します。
- **埋め込みシーン（`disableWindowResize: true`、カスタムコンテナ、祖先要素へのCSSズーム）：** エンジンは意図的に推測しません。自分でコンテナをシーンに配線してください：

```typescript
const scene = new Scene(canvas, { disableWindowResize: true });

const ro = new ResizeObserver(([entry]) => {
  scene.resize(entry.contentRect.width, entry.contentRect.height);
});
ro.observe(container);
// 後片付けのパスでscene.destroy()と一緒に切断してください。
```

`scene.resize(width, height)`は冪等であり、典型的なUIであればデバウンスなしでResizeObserverから呼び出せるほど軽量です。これはまた**再調整フック**でもあります：Firefoxは、ズームやコンテナの変更によって無効化されたレイアウト状態からネイティブの`Range`選択メトリクスを計算します——変更が伝えられなかったシーンは正しくレンダリングされますが、古い座標で**選択**を行います。Firefoxでズーム後に選択ハイライトがずれていてキャンバスは問題ないように見える場合、`resize()`呼び出しの欠落が第一の容疑者です。

## フォント：真のクロスOS変数

`'16px sans-serif'`はOSごとに異なる書体です（Segoe UI、Roboto、San Francisco、DejaVu…）。VectoJSはcanvasの`measureText`を使ってテキストを自身で測定し、レンダラーは同じフォント文字列で描画します——そのため、レイアウトとピクセルはどのマシンでも**互いに**常に一致します。マシン間で異なるのは**絶対的なジオメトリ**です：行幅、折り返し位置、エンティティサイズ。

実際的な影響を、痛みの大きい順に示します：

1. **Webフォントの競合。** Webフォントが読み込まれる前に`Text`/`RichText`/`Markdown`を構築すると、測定はフォールバックフォントを使用し、その後の再描画は読み込まれたフォントで描画します——レイアウトとピクセルが一致しなくなります（内部の一貫性を壊す唯一の方法）。構築をフォントが準備できるまで待機させてください：

   ```typescript
   await document.fonts.ready;
   const label = new Text('Hello', { font: '16px Inter' });
   ```

   コンテンツがフォントの読み込みよりも長く存続する可能性がある場合（レイジーロードされたフォント）、`document.fonts.onloadingdone`ハンドラーから`setText`または`setMaxWidth`を再実行して再測定してください。

2. **ピクセル単位のテスト期待値。** CIが正確なフォントをインストールしていない限り（VectoJSリポジトリはCIにNotoをインストールしています）、テキスト由来の絶対ジオメトリをハードコードされた数値に対してアサートしないでください。関係アサーション（"内部に収まる"、"前の行の下にある"）を優先してください——これはまさに`auditScene`が自動化するものです。

3. **デザインにおける総称ファミリー。** macOSで`'14px sans-serif'`に合わせてカードをサイズ設定すると、Windowsでは正しくありません。フォントを同梱するか、測定によってサイズを決定させる（自己サイズ調整`Text` + コンテナレイアウト）ようにし、想定されるテキスト幅の周りにボックスをハードコードしないでください。

## 重要なブラウザの違い

エンジンのクロスブラウザテストマトリックス（Chrome + Firefox、DPR 1と2、フォント置換）によって特定されたものです。アプリケーションがまだつまずく可能性があるもの：

| 領域                        | 違い                                                                    | 対処方法                                                                         |
| --------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| ネイティブ選択範囲          | Firefoxがズーム/リサイズ後に古いレイアウトから`Range`メトリクスを再計算 | サイジングを自分で管理する場合は`scene.resize()`を呼び出す（上記参照）           |
| `Worker`の可用性            | 一部の埋め込み環境/テストランナーに存在しない→Markdownが同期的にパース  | 機能的には同一；それらの環境ではメインスレッドの時間を確保すること               |
| WebGPU                      | 可用性は環境により異なる；`ComputeParticleEntity`はCPUにフォールバック  | GPUコンピュートをプログレッシブエンハンスメントとして扱う；CPUパスもテスト       |
| モーション抑制              | OSレベルの設定が有効な場合、実効FPSを制限（`respectReducedMotion`）     | 抗わない；設定を有効にしてアニメーションをテストする                             |
| バックグラウンドタブでのrAF | どこでも一時停止されるが、再開のタイミングは異なる                      | エンジンは再開時にアニメーションdtをクランプ；カスタム積分器も自身のdtをクランプ |

## 選択とピクセルの一致を維持する

選択可能なテキストは、**論理ソース文字列**を透明なDOMミラーに投影することで機能し、そのジオメトリはキャンバスペインターと同じレイアウトデータから得られます。整合性は設計上保証されています——それが壊れるときは、短い契約リストのいずれかが破られた場合です：

1. **シーンにサイズ/ズームの変更が伝えられなかった**——古い投影ジオメトリ（特にFirefox；上記の再調整フックを参照）。
2. **測定後にフォントが読み込まれた**——キャンバスと投影は両方とも測定されたレイアウトに従うが、描画されたグリフが移動した（上記のWebフォントの競合）。
3. **カスタムコンポーネントがテキストを描画するが投影していない**——選択可能なミラーのないピクセル、または描画パスとは異なる計算で位置決めされたミラー。カスタムテキストエンティティは、描画と投影の両方にエンジンが準備したレイアウト（`prepareContentGrid` / `LayoutEngine.prepare`）を再利用し、決して2つの独立した測定を行わないでください。

**整合性の検証**（スクリーンショットではなく数値で）：

```typescript
// 1. プログラムによる選択は論理ソースをコピーするか？
//    （選択APIはユーザーがドラッグした場合に生成されるものをミラーリングします。）
const text = window.getSelection()?.toString();
expect(text).toBe(expectedSourceSlice);

// 2. どのエンティティが実際にブラウザの選択イベントを受信したか？
import { createEventTrace } from '@vectojs/devtools/headless';
const trace = createEventTrace(scene, { capacity: 50 });
// … ドラッグ選択 …
// source === 'content' のエントリは選択可能な投影で開始されたもの；
// その targetPath はどの投影かを示し、defaultPrevented は
// アプリケーションがブラウザのデフォルト選択動作をインターセプトしたかどうかを示します。
```

ドラッグ選択テストは、hit-testingと同じ環境マトリックスで実行してください：両方のブラウザ、両方のDPR、そして少なくとも1つの非デフォルトのズームレベル。

## 移植性チェックリスト

どこでも同じように見え、動作するUIのために：

- [ ] 測定に使用するフォントを同梱する；`document.fonts.ready`の後にテキストを構築する。
- [ ] フルスクリーンシーン **または** `ResizeObserver` → `scene.resize()`のブリッジ——どちらもなしは不可。
- [ ] DPR 1 **と** 2、Chrome **と** Firefoxでのポインター + 選択テスト。
- [ ] CIで`auditScene(scene)`がクリーンにパスする（関係型レイアウトの正確性、フォント非依存）。
- [ ] キーとなるインタラクションは、ピクセル比較のスクリーンショットではなく、スナップショット差分（`captureSnapshot`/`diffSnapshots`）を使用する。
- [ ] OSのモーション抑制を有効にしてアニメーションを検証する。
- [ ] WebGL/WebGPUバックエンドが有効な場合、Canvas2Dフォールバックパスもテストする。
