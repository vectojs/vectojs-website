# 为什么选择VectoJS

浏览器DOM是一个强大的通用文档渲染器。它非常适合流式文本、SEO内容、原生表单和中等交互式UI。

当界面的行为更像一个场景而不是一个文档时，它就成了瓶颈。

## 问题

VectoJS针对以下界面：

- 数千个单独动画的项目会产生过多的DOM/样式/布局工作；
- 布局由数学控制，而不是CSS流；
- 命中测试必须匹配自定义变换、曲线和坐标系；
- 相同的UI需要在canvas、WebGL、导出或WebXR上下文中运行；
- 无障碍和自动化仍然重要，即使可见的UI是canvas渲染的。

## 与典型canvas库的区别

大多数canvas库提供绘制原语，并将布局、事件、文本和无障碍留给应用。VectoJS提供了更完整的运行时栈。

| 层       | VectoJS                                  | 典型canvas库     |
| -------- | ---------------------------------------- | ---------------- |
| 布局     | 实体树和布局辅助                         | 手动             |
| 命中测试 | 逐实体命中测试和变换转换                 | 手动             |
| 事件     | 类DOM捕获和冒泡阶段                      | 手动/仅回调      |
| 无障碍   | 符合条件的实体的语义DOM投影              | 通常缺失         |
| 文本     | 布局引擎、换行、BiDi、阿拉伯语、MSDF路径 | 通常仅`fillText` |
| 组件     | 表单、覆盖层、markdown、滚动、布局       | 通常由应用定义   |
| 导出     | 固定步进视频导出器                       | 通常外部工具     |

## VectoJS舍弃了什么

VectoJS用CSS的便利换取显式控制。你拥有更多布局和交互模型：

- CSS不定位单个canvas实体。
- 任意渲染文本的原生文本选择不是自动的。
- SEO爬虫不会将canvas渲染的内容视为页面文本。
- 无障碍通过投影启用，但仍需要正确的标签、角色、键盘行为、对比度和辅助技术测试。
- 实体遍历、更新、语义同步和应用计算仍然消耗CPU；canvas并不能让所有工作免费。

## 何时不使用VectoJS

首先不要使用VectoJS，当：

- 你在构建博客、营销页面、文档站点或CMS页面；
- UI主要是普通表单和表格；
- 渲染内容的SEO可见性是硬性要求；
- 原生浏览器文本选择是产品的核心；
- 没有自定义布局数学、动画密度、图、游戏、模拟或高实体场景。

VectoJS在需要**canvas级别视觉控制**且有足够的运行时基础设施以避免自己重建布局、事件、文本、无障碍和导出时表现最佳。
