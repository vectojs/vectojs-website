# ストリーミングとリアルタイムテキスト

トークンストリーム（LLMチャット）、ログテール、ライブデータフィードは、素朴なVectoJSコードが最も頻繁に破綻する場面です。エンジンは高速なプリミティブ——`Text.append()`、`Markdown.appendMarkdown()`、段落レベルのレイアウトメモ化、オフスレッドのMarkdownパース——を提供しますが、これらをフレーム単位ではなくトークン単位で配線すると、その利点のほとんどが失われます。このページでは、エンドツーエンドのレシピを提供します。

## 唯一のルール：トークン単位ではなく、フレーム単位でバッチ処理する

ストリームは、ディスプレイのリフレッシュ速度よりはるかに速くトークンを届けます。`append()`/`appendMarkdown()`の呼び出しは毎回レイアウトパスを実行し、レンダリングされた2つのフレームの間にあるレイアウトのうち、最後のものを除くすべては**不可視の作業**です。修正方法は4行だけです：トークンが到着したらバッファリングし、アニメーションフレームごとに1回フラッシュします。

```typescript
let pending = '';
let scheduled = false;

function pushToken(token: string) {
  pending += token;
  if (scheduled) return;
  scheduled = true;
  requestAnimationFrame(() => {
    scheduled = false;
    const chunk = pending;
    pending = '';
    markdown.appendMarkdown(chunk); // フレーム全体のトークンに対して1回のレイアウト
    transcript.scrollToBottom();
  });
}

for await (const token of llmStream) pushToken(token);
```

200トークン/秒のストリームを60fpsで実行すると、毎秒約200回のレイアウトパスが約60回になり、負荷がかかっても優雅に劣化します：メインスレッドがビジーであるほど、フラッシュされるチャンクは大きく（そして**まれに**）なります。このパターンは自己調整的です。固定の`setInterval`によるデバウンスではそうはいきません。

> [!NOTE]
> `scene.markDirty()`はすでに自然に統合されています——1フレーム内の3回の追加は1つのフラグをセットし、1回の再描画で済みます。追加の高コスト部分はダーティフラグではなく**レイアウト**であり、そのためバッチ処理は追加自体をラップする必要があります。

## 追加APIの選択

| コンテンツ         | API                                        | 呼び出しごとのコスト                                                                                                            |
| ------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| プレーンテキスト   | `text.append(chunk)`                       | コールドパスだが、完了した`\n`で終わる段落は段落メモによって再利用される                                                        |
| スタイル付きスパン | `richText.appendSpans(spans)`              | スパンを追加；以前のスパンの測定結果は再利用される                                                                              |
| Markdown           | `markdown.appendMarkdown(chunk)`           | rawソースを再レキシング（`Worker`が存在する場合はオフスレッド）、完了したブロックエンティティを再利用、最後の段落をその場で拡張 |
| 任意の内容、置換型 | `setText` / `setContent`（アンチパターン） | 完全再構築——トークン単位で成長するドキュメントに対して決して呼び出さないこと                                                    |

`appendMarkdown`には、知っておくべき2つの隠れたコストがあります：

1. **レキシングはO(ドキュメント)であり、O(チャンク)ではありません。** 呼び出しのたびに、蓄積されたソース全体が再トークン化されます。パースは、利用可能な場合はバックグラウンドのWorkerで実行され（`Worker`がない環境では同期的なレキシングにフォールバック）、エンティティの更新は完了したブロックを再利用します——しかし、10万文字のトランスクリプトであれば、フラッシュごとに10万文字のレキシングコストが依然として発生します。フレームごとのバッチ処理は、これをトークン/フレーム係数で分割します。トランスクリプトのセグメント化（後述）はそれを制限します。

2. **段落メモ化は`\n`をキーとします。** `Text.append`とMarkdown段落更新機はどちらも、変更された段落のみを再測定します。途切れることのない1行が続くとメモ化が機能せず、フラッシュごとにO(ドキュメント)の測定に劣化します。LLMの出力には自然な段落区切りがあります。ログ行は`\n`で終わります——通常は追加の手間はかかりませんが、改行を取り除かないでください。

## タイプライターのペース配分とライフサイクル

パフォーマンスバッチングがデフォルトです。製品がタイプライターの表示を必要とする場合にのみ、固定のウォールクロックベースのペース配分を追加してください：

```typescript
const stream = markdown.createStream({
  pacing: { graphemesPerSecond: 48 },
  maxBufferedChars: 64 * 1024,
  signal: requestAbort.signal,
});
```

ペース配分が「1フレームあたり1トークン」に切り替わることは決してありません。rAFタイムスタンプから `graphemesPerSecond` のクレジットを蓄積し、1フレームで複数の書記素を表示することがあり、依然として最大でも1回の追加コミットを実行します。100msのタイムスタンプ上限により、バックグラウンドのタブが大量の遅れを取り戻すバーストをダンプするのを防ぎます。

スライシングは、チャンク/フレームの境界を越える場合も含め、`Intl.Segmenter` を使用するため、結合マーク、絵文字の ZWJ シーケンス、フラグ、およびサロゲートペアは分割されません。Unicodeでは単一の書記素が無制限に成長することが許可されています；悪意のある入力が境界に達することなく、制限された「受け入れ済み+ブロック済み」のウィンドウを完全に満たした場合、コントローラーはデッドロックしたりメモリを無制限に増やしたりするのではなく、1つのUnicodeコードポイント（決してサロゲートペアの半分ではなく）をコミットします。

- `flush()` は送信されたテキストを同期的にコミットし、ストリームを開いたままにします。
- `close()` はブロックされた書き込みを受け入れ、保持されている書記素の末尾を解放し、順序付けられた最後のコミットを1回実行して、閉じます。
- `abort(reason)` はコミットされていないテキストを破棄します。保留中および将来の操作は、保持された理由で拒否されます。
- `Markdown.setContent()` は、置換を行う前にアクティブなコントローラーを中止します。
- `Markdown.destroy()` はそれを中止し、rAF/`AbortSignal` リスナーを削除します。
- 1つの `Markdown` は最大1つの開いているコントローラーを所有します；後続のストリームが開始できるように、終了したコントローラーは登録解除されます。

## レンダーモードとアイドルスロットル

ストリーミングUIは`renderMode: 'onDemand'`を使用する必要があります：

```typescript
const scene = new Scene(canvas, { renderMode: 'onDemand' });
```

追加のたびにシーンがダーティとしてマークされるため、フレームはコンテンツが流れている間だけレンダリングされ、ストリームがアイドルになると即座に停止します——2fpsの自動スロットルによる驚きも、応答間のバッテリー消費もありません。追加APIと組み込みのスクロールコンテナはすべて、進行中のアニメーションを報告するため（`hasPendingAnimations()`）、最後のトークンが到着した後もスムーズスクロールで最下部までアニメーションし続けることができます。

ストリーム中に`update()`からカスタムの**フレームごとの**モーション（タイピングインジケーター、点滅するカーソルなど）を駆動する場合は、[アイドルスロットルの契約](/learn/performance/#アイドル自動スロットル隠れた落とし穴)を忘れないでください：`hasPendingAnimations()`をオーバーライドするか、`animate()`/`springTo()`で駆動してください。

## 最下部への追従

`ScrollView.scrollToBottom()`はコンテンツの末尾に**スナップ**します——意図的にスクロールスプリングをバイパスしています。なぜなら、スプリングを1秒間に何度も再ターゲットすると、決して落ち着かず、ビューポートが最新のコンテンツを追跡する代わりにジッターするからです。追加と同じrAFフラッシュ内で呼び出し（前述のレシピと同様）、ターゲットが新しいレイアウトの**後**に計算されるようにします。

チャットUIでは、ユーザーの意図に従います：ユーザーがすでに最下部にいた場合にのみ最下部に張り付きます。`content`は公開されており、その`y`は負のスクロール変換値を保持しているため、「最下部」は次のように判定します：

```typescript
function nearBottom(sv: ScrollView, slack = 24): boolean {
  const maxScroll = Math.max(0, sv.content.height - sv.height);
  return -sv.content.y >= maxScroll - slack;
}

// フラッシュ内：追加前に粘着状態を読み取り、追加後に適用。
const stick = nearBottom(transcript);
markdown.appendMarkdown(chunk);
if (stick) transcript.scrollToBottom();
```

1回のフラッシュ内での「読み取り→追加→スクロール」の順序が重要です：追加後に「最下部にいたか」を測定すると、コンテンツが増えたため常に「いいえ」と答えてしまいます。

> [!NOTE]
> 2つのスクロールAPIは意図的に非対称です：`scrollTo(y)`はスクロール**スプリング**を再ターゲットし（そのため`content.y`が次の数フレームでアニメーションしながら移動します）、一方`scrollToBottom()`は**スナップ**します。`scrollTo`の直後に位置ベースの派生状態を読み取ると古い位置が返ります——次のフラッシュで読み取りましょう（上記の粘着パターンが自然にそうしています）。

## 長時間トランスクリプト：セグメント化してから仮想化

追加コストとレキシングコストはどちらもドキュメントサイズとともに増加するため、ドキュメントを制限します。チャット/ログUIの2段階戦略：

1. **メッセージごとにセグメント化。** アシスタントメッセージごとに1つの`Markdown`エンティティを使用し、会話全体に対して1つではありません。ストリーミング中のエンティティは常に小さく（処理中のメッセージのみ）、そのため会話の長さに関係なく、フラッシュごとのレキシングコストは低く保たれます。完了したメッセージはまったく再レキシングされません。
2. **履歴を仮想化。** メッセージが個別のエンティティになれば、[`VirtualList`](/reference/ui-virtuallist/)は表示されているものだけをレンダリングします。1000メッセージのトランスクリプトでも、コストはセッションが蓄積したものではなく、ビューポートに表示されているものだけに基づきます。

```typescript
function startAssistantMessage(): Markdown {
  const md = new Markdown('', { maxWidth: 640 });
  messages.push(md); // あなたのVirtualListデータソース
  return md; // このエンティティにのみストリーミング
}
```

これによりメモリも制限されます：完了したメッセージのレイアウトは静的で削除可能であり、遠くまでスクロールしてもライブテールの再レイアウトはトリガーされません。

## ストリーミングUIの測定

症状とそのシグナルを、確認すべき順に示します：

| 症状                                  | プローブ                                                                                           |
| ------------------------------------- | -------------------------------------------------------------------------------------------------- |
| ストリーミング中のカクつき            | 1秒あたりの追加数と1秒あたりのフレーム数を比較——追加数 ≫ フレーム数の場合、rAFバッチが不足している |
| トランスクリプトが長くなるとカクつく  | 1つの成長し続けるエンティティにストリーミングしている——メッセージごとにセグメント化する            |
| 長い段落でUI全体が停止する            | ストリームに`\n`がない——段落メモが分割できない；ソースのフォーマットを確認                         |
| スクロールがユーザーと競合する        | `scrollToBottom()`を無条件に呼び出している——「最下部にいたか」の粘着判定でゲートする               |
| ストリームがアイドルなのにCPUがビジー | シーンが`'always'`モードのままか、`hasPendingAnimations()`なしのカスタムアニメーションが存在する   |

実際の数値については、[実際のパフォーマンスの測定](/learn/performance/#実際のパフォーマンスの測定)のページ内測定パターンを使用してください——ヘッドレスFPSは代表的ではありません。
