# 환경 간 일관성

DOM 앱은 브라우저의 레이아웃 엔진으로부터 일관성(그리고 비일관성)을
상속받습니다. canvas-네이티브 앱은 **여러분**으로부터 상속받습니다: 엔진은
스스로 측정한 숫자로 모든 위치를 계산하므로, 실패 모드가 이동합니다 —
CSS 특이성에서 벗어나 픽셀 밀도, 확대/축소, 글꼴 메트릭으로 이동합니다.
이 페이지는 각 환경 변수를 실제로 변하는 것, 엔진이 이미 처리하는 것,
그리고 애플리케이션이 해야 할 것에 매핑합니다.

## 기기 픽셀 비율 (HiDPI)

**엔진이 처리하는 것.** 모든 VectoJS 좌표는 논리적 CSS 픽셀입니다.
렌더러는 canvas 백킹 스토어를 `logical × devicePixelRatio`로 크기 조정하고
컨텍스트를 스케일링하며, 모든 `scene.resize()`는 현재 DPR을 다시 읽습니다 —
렌더링, 히트 테스트, 레이아웃 모두 하나의 논리적 좌표 공간을 공유하며,
모든 밀도에서 작동하고 분수 DPR(Windows 125% / 150% 스케일링)도 포함합니다.

**여러분이 해야 할 것.** 런타임에는 아무것도 하지 않아도 됩니다 — 하지만 테스트에서는 모든 것을 해야 합니다:

> [!WARNING]
> 헤드리스 브라우저는 기본적으로 `deviceScaleFactor: 1`을 사용합니다. 대부분의 실제
> 기기는 DPR 2(또는 분수)입니다. DPR에 따라 확장되는 히트 테스트 또는 텍스트
> 프로젝션 오프셋은 기본 헤드리스 실행에서는 **보이지 않고** 첫 번째 실제
> 노트북에서 즉시 드러납니다. 보고된 오프셋이 원점으로부터의 거리에
> 비례한다면, 먼저 DPR을 의심하세요.

`deviceScaleFactor: 2`에서도 포인터 및 선택 테스트를 실행하세요
(Puppeteer/Playwright 모두 컨텍스트별로 노출합니다). 하나의 매트릭스 셀이
전체 버그 클래스를 잡아냅니다.

## 브라우저 확대/축소 및 컨테이너 크기 조정

확대/축소는 유효 DPR과 CSS 뷰포트를 함께 변경합니다. 다음에 일어나는
일은 canvas 크기를 누가 소유하느냐에 달려 있습니다:

- **전체화면 씬**(기본값): Scene이 window `resize` 이벤트를 수신합니다 —
  확대/축소가 이 이벤트를 발생시킵니다 — 그리고 크기, 백킹 스토어, DPR을
  자동으로 재조정합니다.
- **임베디드 씬**(`disableWindowResize: true`, 사용자 정의 컨테이너, 상위 요소의 CSS
  zoom): 엔진은 의도적으로 추측하지 않습니다. 컨테이너를 씬에 직접
  연결하세요:

```typescript
const scene = new Scene(canvas, { disableWindowResize: true });

const ro = new ResizeObserver(([entry]) => {
  scene.resize(entry.contentRect.width, entry.contentRect.height);
});
ro.observe(container);
// scene.destroy()와 함께 정리 경로에서 연결 해제.
```

`scene.resize(width, height)`는 멱등적이며 일반 UI의 경우 디바운스 없이
ResizeObserver에서 호출하기에 충분히 가볍습니다. 이는 또한
**재조정 훅**입니다: Firefox는 확대/축소 및 컨테이너 변경으로 무효화된 레이아웃
상태에서 네이티브 `Range` 선택 메트릭을 계산합니다 — 변경 사항을 전혀 통보받지 못한
씬은 올바르게 렌더링되지만 오래된 좌표에서 _선택_합니다.
Firefox에서 확대/축소 후 선택 하이라이트가 어긋나고 canvas는 정상으로 보인다면,
누락된 `resize()` 호출이 첫 번째 의심 대상입니다.

## 글꼴: 진정한 OS 간 변수

`'16px sans-serif'`는 OS마다 다른 서체입니다(Segoe UI, Roboto,
San Francisco, DejaVu…). VectoJS는 canvas의 `measureText`로 텍스트를
직접 측정하고, 렌더러는 동일한 글꼴 문자열로 그립니다 — 따라서 레이아웃과
픽셀은 어떤 기기에서든 _서로_ 항상 일치합니다. 기기 간에 달라지는 것은
**절대 기하학**입니다: 줄 너비, 줄바꿈 지점, 엔티티 크기.

실용적인 결과를 고통이 큰 순서대로 나열하면:

1. **웹 폰트 경합.** 웹 폰트가 로드되기 전에 `Text`/`RichText`/`Markdown`을
   생성하면, 측정은 폴백 폰트를 사용하는 반면 이후 리페인트는 로드된 폰트로
   그립니다 — 레이아웃과 픽셀이 불일치합니다(내부 일관성을 깨는 유일한 방법).
   생성을 조건부로 처리하세요:

   ```typescript
   await document.fonts.ready;
   const label = new Text('Hello', { font: '16px Inter' });
   ```

   콘텐츠가 폰트 로딩 이후에도 유지될 수 있다면(지연 로드된 폰트),
   `document.fonts.onloadingdone` 핸들러에서 `setText` 또는 `setMaxWidth`를
   다시 실행하여 재측정하세요.

2. **픽셀 정확한 테스트 기대치.** CI가 정확한 폰트를 설치하지 않는 한
   (VectoJS 저장소는 이 이유로 CI에 Noto를 설치합니다), 절대 텍스트-파생
   기하학을 하드코딩된 숫자에 대해 단언하지 마세요. 관계형 단언("내부에
   맞음", "이전 행 아래")을 선호하세요 — 이것이 바로 `auditScene`이
   자동화하는 것입니다.

3. **디자인의 일반 패밀리.** macOS에서 `'14px sans-serif'`에 맞게 카드
   크기를 조정하면 Windows에서 잘못됩니다. 폰트를 직접 포함하거나, 측정값이
   크기를 결정하게 하세요(자체 크기 조정 `Text` + 컨테이너 레이아웃) —
   가정된 텍스트 너비를 기준으로 박스를 하드코딩하는 대신.

## 중요한 브라우저 차이점

엔진의 크로스-브라우저 테스트 매트릭스(Chrome + Firefox, DPR 1 및 2,
폰트 대체)는 다음을 고정합니다; 애플리케이션이 여전히 넘어질 수 있는 것들:

| 영역                | 차이점                                                                | 해결 방법                                                                             |
| ------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 네이티브 선택 범위  | Firefox가 확대/크기 변경 후 오래된 레이아웃에서 `Range` 메트릭 재계산 | 크기 조정을 직접 관리할 때 `scene.resize()` 호출(위 참조)                             |
| `Worker` 가용성     | 일부 임베더/테스트 러너에 없음 → Markdown이 동기적으로 파싱           | 기능적으로 동일; 해당 환경에서 메인 스레드 시간 예산 책정                             |
| WebGPU              | 가용성 다양함; `ComputeParticleEntity`가 CPU로 폴백                   | GPU를 점진적 향상으로 취급; CPU 경로도 테스트                                         |
| 모션 감소           | `respectReducedMotion`(기본값)일 때 OS 설정이 유효 FPS 제한           | 싸우지 마세요; 설정을 켠 상태에서 애니메이션 테스트                                   |
| 백그라운드 탭의 rAF | 모든 곳에서 일시 중단되지만 재개 타이밍이 다름                        | 엔진이 재개 시 애니메이션 dt를 클램프; 사용자 정의 통합자는 자신의 dt를 클램프해야 함 |

## 선택 영역을 픽셀과 정렬 유지

선택 가능한 텍스트는 **논리적 소스 문자열**을 투명한 DOM 미러에 투영하여
작동하며, 그 기하학은 canvas 페인터가 사용하는 것과 동일한 레이아웃 데이터에서
비롯됩니다. 정렬은 구조적으로 보장됩니다 — 깨질 때는 짧은 목록의 계약 중
하나가 위반된 것입니다:

1. **씬이 크기/확대 변경을 통보받지 못함** — 오래된 투영 기하학
   (특히 Firefox; 위의 재조정 훅 참조).
2. **측정 후 폰트가 로드됨** — canvas와 투영 모두 측정된 레이아웃을 따르지만,
   그려진 글리프가 이동함(위의 웹 폰트 경합).
3. **사용자 정의 컴포넌트가 텍스트를 투영 없이 그림** — 선택 가능한 미러가
   없는 픽셀, 또는 페인트 경로와 다른 계산으로 위치가 지정된 미러.
   사용자 정의 텍스트 엔티티는 페인팅과 투영 모두에 엔진의 준비된 레이아웃
   (`prepareContentGrid` / `LayoutEngine.prepare`)을 재사용해야 하며,
   절대 두 개의 독립적인 측정을 하지 마세요.

**정렬 확인**(스크린샷이 아닌 숫자):

```typescript
// 1. 프로그래밍 방식 선택이 논리적 소스를 복사합니까?
//    (선택 API는 사용자 드래그가 생성하는 것을 반영합니다.)
const text = window.getSelection()?.toString();
expect(text).toBe(expectedSourceSlice);

// 2. 실제로 브라우저의 선택 이벤트를 받은 엔티티는 무엇입니까?
import { createEventTrace } from '@vectojs/devtools/headless';
const trace = createEventTrace(scene, { capacity: 50 });
// … 드래그-선택 …
// source === 'content'인 항목은 선택 가능한 투영에서 시작되었습니다;
// targetPath는 어느 것인지 알려주고, defaultPrevented는
// 애플리케이션이 브라우저의 기본 선택 동작을 가로챘는지 알려줍니다.
```

드래그 선택 테스트를 히트 테스트와 동일한 환경 매트릭스에서 실행하세요:
두 브라우저, 두 DPR, 그리고 적어도 하나의 기본이 아닌 확대/축소 수준.

## 이식성 체크리스트

모든 곳에서 동일하게 보이고 동작해야 하는 UI를 위해:

- [ ] 측정하는 폰트를 함께 제공하고; `document.fonts.ready` 후에 텍스트를 생성하세요.
- [ ] 전체화면 씬 **또는** `ResizeObserver` → `scene.resize()` 브리지 — 둘 다 없으면 안 됩니다.
- [ ] DPR 1 **및** 2, Chrome **및** Firefox에서 포인터 + 선택 테스트.
- [ ] CI에서 `auditScene(scene)` 클린(관계형 레이아웃 정확성, 폰트 독립적).
- [ ] 픽셀 비교 스크린샷 대신 주요 상호작용의 스냅샷 차이(`captureSnapshot`/`diffSnapshots`).
- [ ] OS 모션 감소를 활성화한 상태에서 애니메이션 확인.
- [ ] WebGL/WebGPU 백엔드가 활성화된 경우 Canvas2D 폴백 경로도 테스트됨.
